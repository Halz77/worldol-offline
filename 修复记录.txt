22、优化「进入战斗画面卡顿、释放技能卡顿」  √
    前提事实：standalone 包里服务端逻辑与游戏渲染跑在**同一个 WebView 主线程**
              （shims/ws.mjs 的 FakeWebSocket 是同进程内存通道），所以服务端任何一次
              同步存档都会直接把画面冻住。另外战斗中只有 12501(进入)/12502(结束)
              两个协议，技能释放本身是客户端本地计算、不走服务端。
    定位到 4 个开销点：
      A. 进入战斗(12501) 会 commit() 落盘，而这次存档只是为了写一个 1.5 秒的重刷冷却。
      B. SaveStore.save() 用 JSON.stringify(data, null, 2) 美化排版：
         1.15 MB 的存档被排版到 2.7 MB（多出 136%），序列化本身也慢一倍。
      C. save() 一次要写 world.json.tmp / world.json.bak / world.json 三个路径，
         而 VFS 的 persistIfSave 只跳过了 .tmp —— 于是 .bak 和 world.json 各被
         base64 编码并同步写入 localStorage 一次，「一次存档 = 2 次全量编码+2 次写盘」。
      D. 服务端每条消息都 log()，appendFileSync 是「读全量→新建更大数组→拷贝→写回」，
         开销随日志体积线性增长，上限却开到 5 MB（战斗中消息密集，且越玩越卡）。
    修复：· 12501 不再 commit()：冷却只在内存里挡 1.5 秒内的重复触发，
            战斗结束(12502)时会连同战果一起落盘，不影响持久化。
          · save() 改用紧凑 JSON.stringify(data)；盘上不好读，但「导出存档」按钮
            会重新排版（standalone/shims/vfs.mjs 的 exportSave 改成 JSON.parse 后 null,2）。
          · persistIfSave 同时跳过 .bak（和 .tmp 一样）：备份只在内存里有意义，
            没必要占 localStorage 配额、更没必要每次存档多写一份。
          · 日志滚动上限 5 MB → 512 KB。
          · 技能面板补丁 v3 → v4：v3 每次打开面板都无条件 refresh + validateNow +
            下一帧再来一次，而「释放技能」的第一步就是打开这个面板，多出来的同步布局
            正好被感知成卡顿。v4 改为只在 list.numElements 为 0（渲染器确实没建出来）
            时才强制重建，正常情况下零额外开销，自愈能力不变。
    已验证：· 用你的真实存档(1.15 MB / 4 角色)实测一次 save：
              旧 = 序列化 4.7 + base64×2 29.9 ≈ 34.6 ms
              新 = 序列化 2.2 + base64×1  6.8 ≈  9.0 ms  → 提速 3.8 倍
              （Node 侧数值；手机 WebView 的 JS 引擎再慢 3~8 倍，且 localStorage.setItem
                是同步阻塞，实际感知差得更多）
            · 进入战斗由「1 次全量落盘」变为「不落盘」。
            · 全量 tests/*.test.mjs 与改动前一致：pass 231 / fail 53，新增失败 0。
            · 补丁 v4 锚点唯一匹配、二次施加会报错、产物 node --check 通过。

24、战斗卡顿定位：服务端已确凿排除 —— 自动战斗不会来回请求服务器  √（结论）
    现象：进入战斗那一刻卡；每回合第一次释放技能卡一下；中间的技能释放与伤害结算丝滑。
    · 已排除服务端（有实测支撑）：
        - 战斗中客户端与服务端只有 12501(进入) / 12502(结束) 两个协议，
          中间回合一个包都不发 —— 自动战斗不存在"来回请求服务器"。
        - 实测 handleGame(12501) = 0.03 ms（真实存档 1.15 MB / 4 角色）。
        - standalone 的 FakeWebSocket 是同线程内存通道，send() 直接同步调用服务端
          处理，全程没有任何网络请求。
      → 卡顿 100% 在客户端本地。
    · 客户端每回合的一次性路径（已读代码确认）：
        initRoundStartOrder → battle.clearAllPlan() → doAutoFight()
        doAutoFight 在回合开始一次性为所有单位生成行动
        （isUseSkillInitiative → getSkillByID + isCanUse + searchAICursor，
         否则 selectAutoFightTarget + PLAN_ATTACK），随后 doPlanData() 依次执行。
        与"每回合第一次卡一下、之后丝滑"吻合：开销集中在回合开始的决策。
    · 同时排除的嫌疑：
        - BUFF_MAX_SIZE=Infinity 不是元凶：updateBuff 遍历的是固定状态枚举
          BUFFER_POISON..BUFFER_VALUE_MAX(=32)，与 buff 累积数量无关。
        - 战斗模块内没有任何 RES.getRes / loadGroup 之类的资源加载调用。

31、覆盖安装不再需要卸载重装（构建指纹 + WebView 缓存自愈）  √
    原因见第 30 条：站点文件虽然随 APK 更新，但 WebView 会把静态资源的响应缓存到
    App 私有目录，覆盖安装不清私有数据，于是客户端继续吃上一版的主包/资源清单。
    绝大多数用户都是覆盖安装，不可能要求大家为了看改动而卸载丢存档，所以从工程上解决：

    ① 构建期产出构建指纹（build.mjs → app/www/build-version.json）
       · 指纹 = index.html / gd.js / standalone-boot.js / standalone-files.json /
         主包 js / 305.json / worldol-standalone.js / analysis/modules-bundle.json
         的 sha256 前 12 位（本案 73f986b8649a）。内容不变则指纹不变，不误清缓存。
       · 给 index.html 里 19 个 <script src> 与 standalone-boot.js 里动态加载的
         worldol-standalone.js、gd.js 全部加上 ?t=<指纹> —— URL 变了，旧缓存用不上。

    ② 客户端自检（standalone/boot.js 新增 primeChangedAssets）
       · 资源清单 /v/gd/305.json 与主包 js 的 URL 是引擎侧写死的、加不了版本号，
         改用 localStorage 记指纹，发现变了就以 fetch(url,{cache:'reload'}) 重新
         取一次并写回 HTTP 缓存，客户端随后拿到的就是新版。
       · 只在指纹变化的那一次启动执行，日常启动零开销。
       · ⚠ 绝不能清 localStorage：单机存档就在里面（键前缀 worldol-fs:）。

    ③ 原生兜底（MainActivity.java 新增缓存自愈）
       · 读 APK 里的 public/build-version.json，与 SharedPreferences 里上次记录的
         指纹比对，不同就递归删掉私有目录下的缓存目录
         （Cache / HTTP Cache / Code Cache / GPUCache / ShaderCache / WebView），
         再调 WebView.clearCache(true) 补一刀。
       · 删除发生在 super.onCreate() 之前（BridgeActivity.onCreate 会立刻加载首页，
         之后再清就晚了），clearCache 在拿到 Capacitor bridge 之后。
       · 只删缓存目录，不碰 Local Storage / IndexedDB —— 存档保得住。

    ④ ⚠ 踩坑（重要）：构建脚本会静默覆盖原生源码
       安卓打包/构建APK.ps1 里内联了一份 MainActivity 模板，每次构建无条件
       WriteAllText 覆盖 android/app/src/main/java/.../MainActivity.java。
       只改工程里的源码会被下一次构建冲掉 —— 第 7 版第一次构建就是这样：
       dex 里仍是 10/2 编译的旧类（:app:compileDebugJavaWithJavac 直接 UP-TO-DATE），
       APK 静态校验全绿但原生逻辑没进去。
       修法：模板与工程里的源码同步更新，并在模板头部加 `WORLDOL_ACTIVITY_V2` 标记；
       构建脚本识别到该标记就跳过覆盖。**以后改 MainActivity 必须两处同步。**

第 18 版 —— 武器幻化后贴图不跟手（并修掉上一版没生效的守卫）
══════════════════════════════════════════════

【症状】
大锤幻化成剑后：剑不跟角色的手臂、突兀地飘在身后，大锤有时还在。

【根因（客户端角色贴图是两层，两层都只认 icon2）】
  · 躯体模型 = assets/sprite/model/{nameID}.json，决定手臂姿势 + 每个零件的绘制偏移；
    nameID 由 SpriteTool.getSpriteIdByIcon(icon1, icon2, icon3) →
    getSpriteNameIDByWeapon(基础体, 左武器style, 右武器style, 双持, 战斗)
    算出。左右 style 先按 (style-1)>>4 换成「武器类型组」再映射成 113(单手剑)/
    136(双手锤) 等模型；**关键是最后一句 `var l=r;0!=s&&(l=s)` —— 右手会盖掉左手，
    躯体姿势以右手为准**。
  · 武器零件碎片 = getWeaponIcon(左 style, color)，右手只有在双持模型里才是第二个
    零件槽。
  ⇒ 两把武器类型不同时：躯体按右手摆姿势，武器贴图却按左手画 → 贴图与手臂错位
    （飘在身后），右手的武器也照样画出来。

【上一版（v17）为什么没修好】
  v17 的守卫被写成了一个「逗号表达式里的中间语句」：
    …,e=this.bag.getItem(RIGHT),
      !(e&&双手)&&!(左槽双手)&&null!=e&&e.illusionItemId&&…&&(e=t),
      null!=e&&e.icon>0&&(写 icon2)
  if( ) 的条件取的是**最后一个**表达式，中间那句算完就被丢弃 —— 守卫等于没生效，
  右手武器照样写进 icon2，所以症状原样存在。

【本版修法】lib/client-weapon-icon-patch.mjs（weapon-icon-v2）
  1) 左右两槽取到武器后都先做幻化解算（原版只有时装/坐骑有，武器没有）：
     if(x.illusionItemId){var y=this.getIllusionItem(x.illusionItemId,x);y&&(x=y)}
  2) 右手槽加「显示守卫」，并且**挂在最终条件上**（守卫 && icon 检查）：
     仅当满足以下之一才把右手武器写进 icon2，否则右手位不参与渲染 ——
       · 左槽没有可显示武器（空槽 / 盾类 icon=0）→ 只有右手持械的玩家照常显示；
       · 左右「解算幻化后的类型组」相同、且两边都不是双手类型 → 双剑/双刀原样保留；
       · 其余（两把不同类型武器）→ 只画左手，躯体姿势也按左手摆。
     类型组换算与客户端一致：13~23、34~39 用自身；24(盾/护手) 与其它 = 0（无武器姿势）。
     双手集合与 Bag.isTwoHandWeaponType 相同（14/16/18/19/20/22/23/34/36/38/39）。
  实测：主包 4,557,839 → 4,564,108 字符（+711；v17 是 +527），幂等成立。

── 根因（两个，都在客户端） ─────────────
1) 按钮点不动：监听被 doHide 摘掉，而视图是复用的。
   · 幻化按钮的点击原先用 source.onEgret(button, egret.TouchEvent.TOUCH_TAP, …) 注册。
     Mdr 基类的 doHide 是这么收尾的：

     只有闲置超过 Mdr_Dispose_T 才会 dispose。
   · 于是第二次打开时 view.__petIllusionBtn 仍然存在（installButton 早期 return，不再重挂），

         每次界面显示都走一遍 installButton/syncButton 做检查。

     而 doPetSeeMsg 开头有两道「跳过」判断：

第 27 版：美容院造型道具改成原版的「买下即换造型」道具
================================================================

── 问题 ────────────────────────────────
第 26 版把美容院的造型道具做成了 type 12 时装（装备），装备后才改外观。
这不是原版的用法：原版卖的是**买下即生效**的造型道具，点购买立刻换发型/脸型，
道具不进背包、也不占装备栏。用户指出「这些不应该是装备，而是一种道具，
使用之后角色的脸型或发型会转变成相应的贴图」。

── 关键发现：原版客户端本来就支持 ──────
翻主包发现客户端一直有这条链路，只是本地道具的编号没落在它的判定区间里：

· 判定区间写死在 ModelConst（主包）：
    ITEM_ID_HAIR_START = 40100   ITEM_ID_HAIR_END = 40199
    ITEM_ID_FACE_START = 40200   ITEM_ID_FACE_END = 40249
    isHairItem(t){return t>=40100&&t<=40199}
    isFaceItem(t){return t>=40200&&t<=40249}
  注意这判定的是**道具 ID**，不是图标值。

· 购买回包的状态位 == 2 时，客户端直接换造型（主包 t.onItemShopBuy）：
    if(2==p){
      isHairItem(t.id) ? (updateHair(t), refreshWorldSprite())
                       : isFaceItem(t.id) && (updateFace(t), refreshWorldSprite());
      … setPlayerMoney(getInt(), getInt(), getInt()); maxBuy=getShort(); allCount=getShort();
    }
  这一支**不往背包加道具**，也**不走装备流程**——这正是「买下即用」。
  状态 0 才是普通购买（进背包）。

· 造型怎么算：updateHair / updateFace 读的是商品的 **icon** 字段
    updateHair: i = icon - START_HAIR(0)    样式 = 1 + (i-1)/8   颜色 = (i-1)%8
    updateFace: i = icon - START_FACE(1000) 样式 = 1 + (i-1)/8
  而「男性碎片编号」正是 8*style-7+color / 1000+8*style-7，所以：
    **icon 直接等于该款造型的男性碎片编号**（拼图集时已经算出来了，直接用）。
  只有女性贴图的款式用女性碎片也成立：多出来的 +4 落在颜色高位，被 2 位掩码截掉。

── 为什么道具类型仍然是 type 12 ────────
客户端按 type 分派解析分支，而**只有 ITEM_CLASS_ARMOR 分支会读 icon**：
    case e.ITEM_CLASS_ARMOR: t.icon = i.getShort(); …
    case e.ITEM_CLASS_USE_ITEM: t.reqLv = i.getByte(); …（从 reqLv 开始，没有 icon）
改成「普通道具」类型的话 icon 就丢了，客户端拿不到外观值。所以类型保持时装编码，
但道具**只在商店 51/52/55 里出现、买下即换、永不进背包**，行为上就是一件「使用型道具」。

── 第一步：先把「环境噪音」和「真失败」分开 ────────────

这些用例本身有价值，删掉就永远没人会去修；所以**不删代码**，改成按清单忽略。

第 29 版 —— 美容院的造型图标与实际一致 + 点选即可实时预览
================================================================

用户反馈：
  1. 美容师的发型和脸型道具「贴图与实际表现不一样」；
  2. 脱掉时装后，在商店里点选发型/脸型，右边的角色「没有实时预览」。

──────────────── 根因一：点选预览被自己的补丁吃掉了 ────────────────
web/offline.js 里曾为「脱掉时装要恢复角色自己的发型」加过一层基准（baseFaces）：

    Player.prototype.updateIcon = function(){
      ...
      this.icon1.low  = (this.icon1.low  & ~faceLowMask)  | (base.low  & faceLowMask);
      this.icon1.high = (this.icon1.high & ~faceHighMask) | (base.high & faceHighMask);
      ... 原版 updateIcon ...
    };

它的本意是：原版 updateIconByFashion 会把时装的外观直接写进 icon1，所以每轮重建
外观前先把「发型(7..10 位) / 脸型(13..16 位)」还原成角色自己的值，这样脱掉时装后
发型会自己回来。

但商店的「点选预览」（模块 29 的 ModelTool.getCompareSprite）走的正是同一条路：

    复制角色外观 → updateHair(item) / updateFace(item) 改写 icon1 → updateIcon() 重建

于是刚写进去的新造型被 updateIcon 立刻还原 —— 而且基准是 WeakMap 缓存的，
第一次预览之后那个预览模型的基准就锁死在当时的款式上，后面点什么都看不到变化。
（购买回包的 `2 == p` 分支同样调 updateHair 然后 refreshWorldSprite，也被吃掉一次。）

修法：给 Player.prototype.updateHair / updateFace 各包一层，在调用原版之后把基准
同步成新造型。这样基准始终等于「角色当前真正该有的发型/脸型」，
脱掉时装回退原发型的逻辑保持不变，而预览和购买都能立刻生效。

──────────────── 根因二：图标用的是一块「零件」，不是实际的样子 ────────────────
图标图集原先直接拿角色碎片当图：
  · 发型碎片只是一撮头发（23×23 左右，不带脸）
  · 脸型碎片只有一整张脸（17×27 左右，不带头发）
而角色身上是「头发盖在脸上」叠出来的。所以列表图标和实际表现天然对不上；
再加一层：图标固定取男性碎片，女角色看到的也是男款。

修法：图标改成把「脸型碎片 + 发型碎片」按角色画布上的相对位置叠成一张头像。
  · 对齐依据：两类碎片都是从角色画布上紧贴内容裁切的，头顶都压在裁切框顶边，
    所以「水平居中 + 头发盖住脸的上沿约四分之一」就等价于它们在角色身上的位置。
  · 每件道具出两张帧：「<道具编号>」用男性碎片、「<道具编号>f」用女性碎片。
  · 客户端 Tool.getIconByData 的钩子按 icon1 的性别位取图
    （OFFSET_SEX=0 / LEN_SEX=1 —— 这跟渲染时决定用男/女碎片的判断是同一位，
      见 analysis/modules/0055.js：g = icon1.low >> OFFSET_SEX & LEN_SEX）。
  · 图集没就绪时依次退回另一性别、再退回客户端自带的问号图。

npm script：

──────────────── 二、根因：同一个表达式写了两份，第 37 版只改了其中一份 ────────────────

「动态生成给客户端的全局变量」有**两个投放口**：

  服务端路径   lib/http-routes.mjs        —— 把对象 JSON.stringify 进 /equipment-rules.js 正文
  安卓包       安卓打包/standalone/globals.mjs —— 没有 HTTP，直接在 entry 里铺成全局量

同一个表达式在两个文件里各写了一遍。第 37 版把 upgradeIdentifyItemIds 从数组常量改成
函数（为了能惰性加载鉴定表）时，我只批量改了 lib/ 与 web/ —— 而 globals.mjs 既不在 lib/
也不在 web/，那次 grep 根本没扫到它，于是它还是 `identifyItemIds: upgradeIdentifyItemIds`
（函数本身）。客户端 new Set(函数) 当场抛错。

为什么 443 条用例全绿（这是更值得记的部分）：
  · 我写的 HTTP 冒烟只打了**服务端**那一条投放口，globals.mjs 没被任何用例执行过；
  · tests/service.test.mjs 倒是真去 fetch /equipment-rules.js 并求值了，但只断言了
    star.successRate / gem.guaranteed / gem.successRate，**没有断言 identifyItemIds**；
  · 第 38 版补的语法基线也抓不到 —— 那是**类型**错，不是语法错；文件本身完全合法。
  · 一句话：这是一条「两份实现、只有一份被测」的漏网之鱼。

──────────────── 三、修法：收敛成唯一来源，而不是只补那个括号 ────────────────

只把 globals.mjs 那行补上 `()` 能修好这次，但下次改这份对象还会漏。按评审 P0-2
（补丁链双份）同样的处理方式收敛：

  新增 **lib/generated-globals.mjs** —— 这两个对象的唯一实现：
      equipmentRulesGlobals()   → { ...upgradeRules, advanced:{...,identifyItemIds:…()}, spirit }
      compositionGlobals()      → { vipMax, sets }
  两边都改成调它：
      lib/http-routes.mjs                用 equipmentRulesGlobals() / compositionGlobals()
      安卓打包/standalone/globals.mjs    同样的两个调用，文件里写清「别再抄表达式」

顺带清掉**第三份**照抄：tests/equipment-workshop.test.mjs 里
`const browserRules={...upgradeRules,advanced:{...,identifyItemIds:upgradeIdentifyItemIds()}}`
也改成 `equipmentRulesGlobals()`。它当时的注释还写着「这里照抄同一份，免得测试里的规则和
真正下发的不一致」—— 照抄正是分叉的来源。

──────────────── 四、守卫：把「两个投放口必须一致」变成断言 ────────────────

新增 tests/generated-globals.test.mjs（5 条）。做法是把三条生成脚本
（/equipment-rules.js、/equipment-composition-data.js、/pet-snapshot-data.js）从路由表里
取出来、在 vm 沙箱里求值，再和 globals.mjs 的导出逐字段对一遍：

  1. 两条投放口给的形状逐字段一致；
  2. **这些对象必须是纯数据，不许有函数漏进去** —— 函数进 JSON.stringify 会被静默丢掉，
     两条路给客户端的字段就不一样了（这一条就是本次事故的直接断言）；
  3. 客户端会 new Set / 展开的字段必须是数组（identifyItemIds / identifyScrolls /
     starScrolls / star.bands / sets）；
  4. 每条生成脚本定义的全局量，entry.mjs 都得铺上（数量钉死，防止加了第 4 条脚本却
     忘了同步）；
  5. build.mjs 的 generated 列表与路由表对得上（少摘一条客户端会去请求不存在的静态文件）。

负向实验：把 lib/generated-globals.mjs 里的 `identifyItemIds:upgradeIdentifyItemIds()`
改回不带调用 → 第 2、3 条立刻红，报错信息就是「equipmentRules 里有函数值 ——
JSON.stringify 会把它静默丢掉…」；恢复后 5/5 通过。

写用例时踩到的坑（记下来，别人的测试也会踩）：vm 沙箱里的对象属于**另一个 realm**，
原型不是宿主的 Object.prototype，而 assert/strict 的 deepEqual 是 deepStrictEqual、
要连原型一起比 —— 直接比会报「不一致」却看不到任何字段差异（我第一版就栽在这儿，
用自己的 walk() 逐字段比才发现两边其实完全相同）。两边各过一次 JSON 往返再比即可，
这也正好把「客户端实际拿到的形状」定死了。
