# 世界OL 单机版 · 架构评审（2026-10-11）

评审对象：`世界OL_源码/世界online_原版单机/` + `安卓打包/`。  
所有数字都是在这台机器上实测出来的，不是估算。

---

## 一、现状：这套东西是怎么跑起来的

运行形态有两条路，但**共用同一份服务端代码**：

|     | 本机跑                              | 安卓跑                                                                 |
| --- | -------------------------------- | ------------------------------------------------------------------- |
| 入口  | `node server.mjs`                | 同一个 `server.mjs` 被 esbuild 打进 `worldol-standalone.js`，在 WebView 里执行 |
| 网络  | 真 HTTP + WebSocket(ws)           | `shims/` 把 http/ws/fs/crypto/path 换成内存实现，请求走 XHR、存档走 localStorage   |
| 客户端 | `client/` 原版主包**运行时字符串补丁**后吐给浏览器 | 同上，只不过"运行时"= WebView 启动时                                            |

代码分层与体量：

```
client/           148 MB   原版 v305 归档资源，字节不可改（测试断言 sha256）
data/             161 MB   抓包 / 录制 / 社区复原 / 本地手写的配置 JSON
analysis/          15 MB   反编译出来的 gd.decoded.js + 1613 个客户端模块
lib/           114 个文件   6,036 行   单机版"服务端"全部逻辑
  ├─ *-service.mjs   20 个            协议处理器
  ├─ client-*-patch.mjs 17 个         对原版主包做字符串注入
  └─ 其余              77 个          内容数据 / 规则 / 编解码 / 存档
web/            23 个脚本   2,328 行   追加在页面上的 DOM 逻辑
tests/          65 个文件   6,480 行   370 条用例（其中 47 条长期失败被忽略）
server.mjs         268 行             上帝文件：HTTP 路由 + WS 分派 + 生命周期
安卓打包/standalone/build.mjs         把上面这些打成一个浏览器可跑的 bundle
```

一句话总结：**这不是一个"重写过的单机版"，而是一个"把原版客户端当黑盒、在它外面贴标签、再用一个 JS 服务端喂它"的兼容层。** 这个定位是对的——毕竟原版客户端是压缩过的 4.5 MB 产物，改不动也不该改。问题几乎都出在这层兼容层自身的工程化上。

## 二、问题清单

### P0-1　整个工程不在版本控制下

`git rev-parse` 直接报 `fatal: not a git repository`。

这个工程的对象是：4.5 MB 的压缩 JS、161 MB 的 JSON、300 MB 的归档资源，以及一套**靠字符串匹配改客户端**的机制（`replaceOnce()` 匹配失败就抛异常）。在这种组合下没有 git，意味着：

- 补丁写错一个字 → 抛 `Client patch mismatch` → 只能靠 `修复记录.txt`（185 KB 纯文本）和 `backups/` 手工回溯；
- 没法 `diff` 出"上一版和这一版到底改了什么"；
- 没法开分支试一个改动，试验失败就回不去；
- 78 个测试临时目录、`logs/`、`saves/`、`qa-v05-saves/` 全混在工作树里，也没法用 `.gitignore` 规整。

**这是唯一一个会让其它所有问题变得不可收拾的问题。** 先做这个，成本最低（半小时），收益最大。

> 建议：`git init` + 一份 `.gitignore`。`client/`、`node_modules/`、`test-*/`、`logs/`、`saves/`、`安卓打包/app/` 全部忽略（这些要么不可改、要么可重建），只把 `lib/ tools/ web/ tests/ data/ server.mjs 安卓打包/*.ps1 安卓打包/standalone/ 修复记录.txt` 纳入。首commit 应该是当前这份"能跑通、测试新增失败为 0"的状态。

### P0-2　客户端补丁链写了两份，没有任何东西守着它

`lib/client-*-patch.mjs` 共 17 个补丁函数、54 处 `.replace()`，靠 `replaceOnce()` 断言"待替换片段必须恰好出现一次"。

补丁链在**两个地方各写一份**：

- `server.mjs:89-90`
- `安卓打包/standalone/build.mjs:85-104`（注释原话：「server.mjs 里的补丁链顺序必须与这里一致」）

实测两条链的顺序目前是一致的，但**没有任何测试守着**。`tests/legion.test.mjs` 只测单个补丁函数自身的幂等性，不测链。

风险很具体：下次加第 18 个补丁，改了一边忘另一边 → 构建期或运行期直接抛异常；顺序写岔 → 两个补丁抢同一段文本，其中一个匹配不到。

> 建议：把链提到**一个共享模块**里（例如 `lib/client-patch-chain.mjs` 导出 `applyClientPatches(source)`），`server.mjs` 和 `build.mjs` 都调它；再补一条用例断言"这个模块导出的补丁数量/顺序指纹"和 `修复记录.txt` 里记的一致。改动量很小，一次性消掉最容易出事故的重复。

### P1-1　启动就吃 528 MB 内存，数据全量常驻

实测（`node -e "import('./server.mjs')"`）：

```
import 完成耗时        1,714 ms（冷盘时 60 s，见下方注）
进程 RSS               528 MB
heapUsed               302 MB
```

单独量 `import('./lib/store.mjs')`（它会牵进整张数据图）：**890 ms，RSS 直接 43 MB → 318 MB**。

各 JSON 解析后的常驻增量（实测）：

| 文件                               | 原始大小    | 解析后常驻  |
| -------------------------------- | ------- | ------ |
| content-library.json             | 25.2 MB | ~48 MB |
| official-v305.json               | 32.9 MB | ~29 MB |
| skill-progression.json           | 13.2 MB | ~26 MB |
| career-skill-directory.json      | 9.4 MB  | ~19 MB |
| recorded-content.json            | 17.0 MB | ~15 MB |
| recorded-expansion-20260922.json | 12.1 MB | ~11 MB |
| career-skills.json               | 7.5 MB  | ~8 MB  |
| pet-catalog.json                 | 6.4 MB  | ~8 MB  |
| 其余零散                             | —       | ~15 MB |

问题在于**这些数据里很大一部分只在特定面板才用得到**（技能图鉴、道具图鉴、录制内容、装备词条表……），却在启动时被 `lib/*.mjs` 顶层的 `JSON.parse(fs.readFileSync(...))` 全部解析进堆。

有意思的是 HTTP 层已经做对了：`/api/xxx` 接口都是**按需读取**的（`server.mjs:136` 就是现读现发）。**只有 `lib/` 侧还在 eager import。**

在安卓上跑的是同一套代码，WebView 的堆更紧张，同时还要再装 4.9 MB 预载资源。

> 建议（按性价比排序）：
>
> 1. 把 `lib/*.mjs` 顶层解析改成惰性 getter 或 `createRequire` 式的按需加载，只保留服务端**每次连线都要用**的那几份（`content.mjs` 的地图/NPC、`official-data` 的规则索引）。
> 2. 面板数据一律走已有的 `/api/*` 接口，lib 侧不再 import。
> 3. 长期看，把 `data/` 里几份大 JSON 转成按 id 分片的索引 + 分片文件，用多少读多少。

> 注：第一次测量时 `import` 花了 **60 秒**（冷盘/杀软扫描 161 MB JSON + 148 MB 客户端），第二次起稳定在 1.7 秒。也就是说**首次启动体验与后续启动完全不是一个量级**——这在安卓上同样成立（覆盖安装后第一次开 App）。

### P1-2　测试有一个 47 条的"永久红"基线

`tests/known-failures.json` 让运行器忽略 47 条长期失败，判定标准是"新增失败 = 0"。

这个机制本身是合理的过渡手段（老用例期望的是早期单机版的行为与数据规模，不是 bug）。但它有个副作用：**这 47 条用例实际上已经不作数了**——它们保护不了任何东西，而且如果哪天真的被改坏了，也看不出来（因为一直红着）。

分布上也不均匀：`city-character-features` 一家占 7 条、`player-experience` 4 条、`game` 3 条，其余都很零散。

> 建议：把这 47 条逐条分类处理，而不是长期挂着——
>
> - 期望值过时的 → **改期望值**（改完 `node tools/run-tests.mjs --update`）；
> - 依赖已删素材的 → 参考 `fashion-icons.test.mjs` 的做法，改成**显式条件跳过并写明原因**（`t.skip('源目录已清理')`）；
> - 确实在测废弃功能的 → **删掉**。
>
> 目标是让 `known-failures.json` 最终归零。一个全绿的套件才是有信号量的套件。

### P1-3　构建期已经打过补丁，运行期又打一遍

`build.mjs` 的注释写得很清楚：

> `// 主包：VFS 里用原始版本（server.mjs 还要自己打一遍补丁）`  
> `entries.push({ vfs: '/worldol/client/' + MAIN_PATH, url: '/' + MAIN_PATH + '.orig' })`

于是实际发生的是：

1. 构建期：读原包 → 打完整补丁链 → 写进站点（4,557,839 → 4,564,108 字节）；
2. 启动时（本机是起服务，安卓是开 App）：把 `.orig`（4.9 MB）读进内存 → **再打一遍完整补丁链** → 才吐给浏览器。

也就是说：**构建期的补丁产物基本被浪费了（只用于另一个 URL），而最贵的一步每次启动都在重做。** 实测这条链在 Node 上约 840 ms（其中 `patchCombatLimits` 一个人占 720 ms，是正则全量扫描），WebView 里还要更慢。

更麻烦的是这带来一个隐性约束：「VFS 里必须保留未打补丁的原件，否则 server.mjs 二次打补丁会报错」。这个约束只存在于注释里。

> 建议：让运行期直接使用构建期产物——`build.mjs` 把打过补丁的版本同时登记为 VFS 的 `client/<MAIN_PATH>`，`server.mjs` 在"源已经是打过补丁的"情况下跳过补丁链（可以靠一个构建期注入的标记常量判断）。顺带把 `patchCombatLimits` 从"全量正则"改成"先 indexOf 定位再局部替换"，把 720 ms 压下去。

### P2-1　`server.mjs` 是上帝文件，且协议号是裸数字

268 行里塞了：70+ 个 import、20 个内联 `type === NNNNN` 分支、一张 23 项的 HTTP 路由表、日志系统、两个定时器、WebSocket 全生命周期。

分派方式是**一条 20 层的顺序敏感链**：

```js
if(handleCharacterFeatures(type,r,context,{...}))return;
if(handleLegion(type,r,context,{...}))return;
...
if(handleGame(type,r,context,{...}))return;   // 必须最后
```

新增一个服务必须回来改这里；顺序错了（比如把 `handleGame` 提前）会静默吞掉别人的包。

协议号全是裸数字（`type===10002`、`type===90022`、`type===12019`…）。而 `analysis/modules/0019.js` 里其实有一份**完整的协议枚举表**（`CG_COUNTRY_WAR_SEE_LIST = 15052` 这种），现在只被用来取 4 个常量（`server.mjs:265`）。

> 建议：
>
> 1. 用 0019.js 自动生成一份 `lib/protocol-constants.mjs`，把裸数字换掉；
> 2. 分派表化：`const HANDLERS = [handleX, handleY, ...]` 或 `{type: handler}` 映射，链条改造为循环；
> 3. HTTP 路由表抽到 `lib/http-routes.mjs`；
> 4. 顺手产出一份「已实现协议 vs 全量协议」的覆盖率报告（`/api/status` 里的 `unknown` 集合已经是现成的原料）。

### P2-2　仓库卫生：78 个测试临时目录躺在工作树里

```
$ ls -d test-captured-expansion-* test-save-check-*  | wc -l   →  78
$ du -ch test-* | tail -1                                      →  624 K
```

原因是测试用 `fs.mkdtempSync(path.join(root, 'test-captured-expansion-'))` —— **建在仓库根目录**，而且 `tests/recorded-expansion.test.mjs:27` 那条干脆没有清理。

同时 `logs/session.jsonl`、`saves/`、`backups/`、`qa-v05-saves/`、`default-save/`、`runtime/` 也都在工作树里。

> 建议：测试临时目录一律用 `os.tmpdir()`；统一用 `t.after(() => fs.rmSync(dir,{recursive:true,force:true}))` 收尾；清掉现存 78 个；`.gitignore` 里把上面这些运行时目录排掉。

### P2-3　改客户端行为有两个入口，边界不清

现在想改客户端行为，可以往两个地方写：

- `lib/client-*-patch.mjs`：把代码**字符串注入原版主包**；
- `web/*.js`：作为**额外脚本**挂在页面上，`web/index.html` 里 23 个 `<script>` 按隐式顺序加载。

两者能力重叠（都能改同一个功能），但约束完全不同：前者要小心匹配片段、要同步两处链、有 4.5 MB 扫描成本；后者受限于"原版代码执行到哪一步"，得靠 `window.xxx` 打洞。

`web/offline.js` 379 行里就同时包含了 `Tool.getIconByData` 钩子、`Player.prototype.updateIcon` 包装、商店白名单这些补丁式代码。

> 建议：写一条明确的分工规则并写进 `修复记录.txt` 顶部的约定区，例如：  
> **能靠页面脚本 + 官方扩展点做到的，一律不动主包**；只有"必须在原版内部逻辑中间插一刀"（如战斗结算、协议解析）才用主包补丁。  
> 顺带把 `index.html` 的脚本顺序变成显式依赖注释（哪些脚本必须在 `offline.js` 之前）。

### P3-2　161 MB 数据没有血缘文档

`data/` 至少四类来源混在一起：

1. **官方抓包**：`official-v305.json`、`recorded-expansion-20260922.json`
2. **社区 H5 复原**：`content-library.json`
3. **正式服录制**：`recorded-content.json`
4. **本地手写/生成**：`fashion-icons.json`、`local-*.json`、各 `*-rules.json`

而 `official-v305` / `content-library` / `recorded-content` / `career-skills` 之间存在**语义重叠**（都含有"技能""道具"的概念），却没有任何一份说明写清谁是谁的权威来源、谁覆盖谁、哪个 `tools/` 脚本能重新生成。

`lib/official-data.mjs`、`lib/recorded-content.mjs`、`lib/career-skills.mjs` 三套"技能/道具目录"并存，未来加功能时很容易查错表。

> 建议：写一份 `data/SOURCES.md`，逐文件列出〔来源类型 / 采集时间 / 生成它的 tools 脚本 / 是否可重建 / 与其它文件的覆盖关系〕。这份文档比任何重构都省事，但能减少大量"改了 A 结果 B 才是生效的那份"的返工。

## 四、值得保留的设计（别改坏）

评审里也要说清楚哪些是做对了的，避免以后重构时误伤：

- **`tests/run-tests.mjs`**：绕过环境 shim、解析 TAP、按清单忽略已知失败、只对新增失败退出 1 —— 这个运行器设计得相当专业。
- **`SaveStore.save()`**：写临时文件 → 备份 `.bak` → 原子 rename，且存档用紧凑 JSON（省一半体积）。改存档逻辑时不要破坏这个顺序。
- **`lib/native-ui-restoration.mjs` 的做法**：归档原件 `client/v/gd/305.json` 字节不动，所有补充只在内存里生成的那份清单上做；测试断言原件 sha256。这是"不破坏原版资源"的正确姿势，应该继续遵守。
- **`standalone/shims/`**：把 node 的 fs/ws/crypto 换成内存实现，让同一份服务端代码能在浏览器里跑。这层抽象很值钱，是"一份代码两个平台"的关键。
- **`replaceOnce()` 的"恰好一次"断言**：虽然补丁链本身脆弱，但"匹配失败就抛错、绝不静默跳过"这个选择是对的——它把问题暴露在构建期而不是运行期。
