# 对比报告：社区版「无神器自制龙宫」APK vs 本工程

> 对比对象：`C:/Users/hal/Desktop/无神器自制龙宫.apk`（社区其他开发者制作，2026-10-25 分析）。
> 方法：解包 APK → 与 `安卓打包/app/www/`（本工程 10-24 构建）逐层对比：服务端打包（worldol-standalone.js）、客户端补丁（js/ff 主包 + gd.js）、web 层（offline.js 等）、数据层（data/ 全量 ID 集比对）。

## 3. 移植清单

### 已决案（2026-10-25）

**① boss 直达挑战重复接取 —— 已移植**
- 他们的做法（`official-rules.mjs` MOD，数据驱动）：
  ```js
  repeatableChallengeMissions = new Set([3042,
    ...[...officialMissions.values()].filter(q=>q.localChallenge&&q.mapId===277).map(q=>q.id)]);
  ```
- 我们的旧现状：`repeatableChallengeMissions` 只有 `{3042}`，地图 277 的 39 个 `localChallenge` 任务交完就关门。
- 已落地：`lib/official-rules.mjs` 按同款数据驱动实现（**懒求值**——建模块时访问 `officialMissions` 会把整张数据图拉进堆，第一次用到时才算并缓存）；新增 `tests/boss-hub.test.mjs` 4 个用例守护（39 个挑战战斗数据齐全、9106 已修、全部可重复、小白传送菜单在位）。

**② 存档导出到手机 Download 目录 —— 不移植**（用户 2026-10-25 决定）
- 原评估：他们的实现是 `standalone-boot.js` 的 `MOD(save-export-native)`——悬浮按钮 + `Capacitor.nativePromise('SaveFile','saveToDownloads',…)` 写 `/storage/emulated/0/Download/`（MediaStore 免权限）；还修了 `seedInitialSave()` 与 `restoreSaves()` 的顺序问题（原来「有没有存档」永远问不出，`exportSave()` 恒 null）。
- 不搬原因：需要 Capacitor 原生插件 + `构建APK.ps1` 的 MainActivity 两处同步，成本高于收益；现有游戏内导出够用。

**③ 战斗结算诊断钩子 —— 不移植**（用户 2026-10-25 决定）
- 原评估：他们拦截 12502 回包，`battleDiagnostic()` 采集双方存活数、各位置单位类型/hp/有效位，result≠2 时写进诊断记录。纯诊断、不影响结算，约 40 行。

### 可选移植（设计取舍，你定）

**④ 宠物蛋等级同步人物等级（上限 97）**
- 他们把 `levelPetTo(p,pet,90)` 改成 97 并让蛋同步人物等级；我们固定 90。
- 影响：小号玩家孵化出来就是当前等级（原版体验）；我们 90 级是 convenience 选择。
- 成本：1 行。风险：低。**但这改变平衡节奏，建议作为选项而非默认。**

**⑤ 阵法书的 type 28 路线**
- 他们阵法书用 type 28 消耗品 + power1=182，客户端原生就走 `POWER_FORMATION_BOOK` 分支发 14012，**完全不需要客户端补丁**；我们 type 31 和人物技能书撞型，靠补丁让路。
- 不建议现在改（我们的 16 阵已上线验证过），但**以后再往阵法加内容、或做类似「使用后走专属协议」的道具时，优先学他们用 type 28**，可以省掉补丁和补丁链长度测试的维护。

### 不建议移植

- **他们的 40 个直达挑战任务本体**：我们已有同内容（9100—9138，39 个），且他们的 2 个额外 BOSS 我们也有（守卫挑战 8932/8933）。搬数据只会造成 ID 双轨。
- **他们的 8 阵四圣兽阵法**：与我们 16 阵内容重复且已上线；两套并存会让玩家困惑。
- **他们的初始空存档**：与「打包默认存档」的需求相反。
- **他们的主包构建**（另一个 v305 构建 +232 补丁）：我们的补丁链深得多，换基线等于推倒重来。
- **新建角色默认开音乐**：我们默认关是用户既有偏好，不回头。

## 4. 对比中发现的我们自己的 BUG（已修）

**直达任务 9106「挑战太阳神-库库尔坎」的编队 20500 不存在 —— 2026-10-25 已修。**
- 全量扫描 39 个直达任务：38 个编队/怪物齐全，仅 9106 的 `acceptBattleID=20500` 在 `official-v305.json` 与 `recorded-expansion` 里都没有 → `missionBlockers` 会以「剧情战斗数据尚未采集」挡掉，该 NPC 接不了任务。
- 已落地：`lib/boss-hub.mjs` 的 `repairKukulkanBattle()` 把 9106 的 acceptBattleID 从 20500 改指 **11781**（含怪物 3352 太阳神-库库尔坎，与征战广场 945:5 的挑战同一只怪），照 `dungeon-repairs` 的运行时修补模式，**不动 data/**，幂等。
- `tests/boss-hub.test.mjs` 补了「39 个直达任务 missionBlockers 全空」的断言——这条断言本来就不该没有。

## 6. 方法论备注（给下次对比）

- 版本基线：比 `gd.js` 哈希（同源则引导补丁一致）、比 offline.js 时间戳与功能标识符、比 standalone 包里模块路径注释。
- 内容差异：对 `data/*.json` 做 **ID 集比对**（任务/道具/怪物/编队/地图五类），比文件大小更能说明「谁缺什么」；文件大小差异大多来自双方后续导入量不同（我们的 official-v305 大 10.8MB，但内容是他们子集+我们新增）。
- 陷阱：对方公告/文档里声称的「缺失」可能只验了 ID 存在性（本次 77/78/86 的教训），必须验引用关系。
