## 第 55 版 · 一键打包.bat + 宝石替换“幽灵宝石”修复

### 一、新增 `安卓打包/一键打包.bat`（傻瓜式打包，双击即用）
四步：环境自检 → `node standalone\build.mjs` → `构建APK.ps1` → 归档到 `output\worldol-<时间戳>.apk`
（打印体积/站点指纹/SHA256，output 只留最近 5 个）。参数：release / fresh / noopen / nopause。

实测跑了三轮（每轮 7–8 分钟，gradle 增量只 14s，大头是站点构建 + cap sync），退出码 0 ✓。

**踩的坑（都写进 MEMORY.md 了）**：
- **bat 必须 GBK(936) + CRLF**：cmd 永远按系统 ANSI 读 .bat，`chcp` 只管输出不管解析。
  存 UTF-8 → 中文乱码，更糟的是某些 UTF-8 字节被 GBK 解释后落在 cmd 分隔符上，
  **把一行拆成两条命令**（实测一句中文提示被当命令执行、脚本报错退出）。
- `echo ... -> app\www` 的 `>` 被当重定向，生成了垃圾文件 `app\www）`。
- ps1 自己固定 UTF-8 → bat 调它前 `chcp 65001`、调完立刻 `chcp 936`。
- 用 Edit 改过 bat（工具写 UTF-8）后必须转回 GBK：`[IO.File]::WriteAllText($p,$t,[Text.Encoding]::GetEncoding(936))`。

### 二、宝石替换后留下数量为 0 的“幽灵宝石”（玩家反馈）
- 现象：替换宝石每次在背包剩“一颗”加4宝石，既不能镶嵌也不能出售。
- 根因：`lib/equipment-upgrades.mjs` 的 `planGemReplace()` 清空用尽槽位写成
  `filter(i=>(i.quantity||1)!==0)` —— quantity=0 时 `(0||1)=1`，**恒为真 = 没过滤**，
  于是留下 `quantity:0` 的条目；客户端按 1 颗显示，镶嵌时 `consume()` 要求 `>0`、
  出售时数量对不上 → 谁也用不了。同文件 `consume()` 与 `bag-actions.mjs` 的 `remove()`
  写法都是对的，**这是全库唯一一处**。
- 触发条件：替换消耗 `2×已镶颗数`（客户端 `2*e.attachDone`，服务端一致），
  宝石数 2N 或 2N+1 时就会正好用尽某一格。
- 修复：`filter(i=>i.quantity!==0)` + 3 条用例（单槽用尽 / 多槽用尽 / 对照：真剩 1 颗能卖 500）。
- 教训：`x||默认值` 这种写法不能用来判断“是否为零”，**`0` 会被默认值吃掉**。

## 追加 · 排查「每次打包后回收站多出好多垃圾、删起来特别卡」

**结论：不是游戏/脚本的 bug，是构建过程 + 这台机器的删除语义共同造成的。**

证据（直接读回收站 `$I` 索引解析原路径）：
- F 盘回收站 42447 条，**全部来自** `安卓打包\app\android\**\build\**`
  （Gradle 的 mergeDebugAssets / compressDebugAssets 中间产物：.json 21753、.png 18641、.jar 20…）
- 时间戳与我跑打包的时刻完全吻合（10/15 09:15:27–30 一分钟内 4 万条）
- 对比实验：`%TEMP%` 里建文件 → `Remove-Item` 删除 → **回收站里没有**；
  项目目录里建文件 → 同样方式删除 → **回收站里出现**
- 结论：**项目目录内的删除被工作区的“安全删除”策略重定向到了回收站**，`%TEMP%` 不受影响

为什么量这么大：站点 `app/www` 有 9999 个文件，Gradle 每次构建都重建 assets 的
merge/compress 中间产物（约 1.5–2 万个文件），删旧建新 → 全部进回收站，累积到 4.2 万条，
资源管理器清空要逐个处理所以特别卡。

交付：`安卓打包/清理回收站.bat`（GBK+CRLF）—— 统计条目数 → 明确警告 → 输入 Y 才
`Clear-RecycleBin -DriveLetter <盘> -Force`。实测统计 42447 条耗时 1 秒；用 `N` 走取消路径验证过。
用户自己双击打包（不在工作区里跑）时删除是直接删，不会往回收站堆。

**学到的一条环境知识**：在这个工作区里"删掉文件"≈"丢进回收站"，所以任何会产生大量临时文件
的构建/测试都不该在这里反复跑（或者跑完自己清）。已记进 MEMORY.md 的环境段。

## 第 57 版 · 技能覆盖在 APK 里一直静默失效（真凶：existsSync + VFS）

第 56 版修完 info 后重打包，用户看游戏里 129 仍是原版效果（**连效果行都没变**）→ 说明
覆盖根本没生效，不只是说明文字的问题。

根因：APK 里 node:fs 是 VFS shim，`existsSync` 只查「已预载」的内存表，而
`standalone-boot.js` 读 `standalone-files.json` 预载的清单**只有 6 个文件、不含任何 data/**；
data 资料是运行时按需同步 XHR 取的。而覆盖层写的是
`if(!fs.existsSync(FILE)) return {revision:null,skills:{}}` —— 恒走空分支 →
**第 54 版以来所有技能覆盖（人物/装备/怪物）在 APK 里从未生效**。
之前几次我都是在源项目里用 Node 真 fs 验证（真 fs 上 existsSync 正常），所以一直没测出来。

实证（拿站点真实 shims/vfs.mjs + 假 XHR 在 Node 里跑）：
  vfs.has("/data/local-skill-overrides.json") → false（= existsSync 看到的）
  vfs.readText(同路径)                       → 2496 字符，含 129、437
  vfs.has("/data/career-skills.json")         → false（连一直正常的表也是 false）
  vfs.readText("/data/career-skills.json")    → 7,832,001 字符
  → 后者一直没事，就因为没拿 existsSync 做门控

修：覆盖层与 fashion-icons 都改成 `try{readFileSync}catch(e){if(e?.code==="ENOENT")…}`
（未命中会触发按需加载）。fashion-icons 的 client/assets 存在性探测也一并去掉（同样恒 false）。
守卫：tests/skill-editor.test.mjs 断言 lib 里除 store.mjs（存档在可写层）/ http-routes.mjs
（PC 静态服务）外不得出现 existsSync；另加 fashionIconData 的降级用例。

验证：npm test 75 文件 / 505 用例全过（新增 2 条），check 293 文件 0 错。
包内核验：`loadData` 已是 try/catch 版，`existsSync(FILE)` 残留 0。
APK：`output/worldol-20261017-092039.apk`（123.4MB，站点指纹 2742e66f31d8，
sha256 5075564159b16ccdfe6f460f6fe8fd5a562d0baa78aa93f2294b7e1614275bcd）。
