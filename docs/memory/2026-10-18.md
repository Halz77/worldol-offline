# 2026-10-18 · 第 69 版

## 主题：永泽塔挑战进战斗 —— 补上客户端桥接

### 症状
主界面「永泽塔」→ 塔层目录 → 某一层，点「挑战 / 实战 / 模拟战」没有任何反应，进不了战斗。
这是上一轮「修一半」留下的状态。

### 定位
- 服务端第 61 版就完整实现了 30001/30003/30005/13101（扣次数、回 30004、推塔组、
  12501 开战、12502 结算、扫荡 30005），所以问题只在客户端。
- `web/home-features.js` 里有一处**占位补丁**（基线 `2bbe512` 起就在）：
  ```js
  const Tower=req(1500).default.prototype;
  for(const name of ['sendClimbTowerChallenge','sendClimbTowerSweep'])
    Tower[name]=()=>UI.alertMessage('战斗阵容、技能、AI与场景尚未录全，挑战和扫荡待补。…');
  ```
  它把原生发送直接换成弹窗 → 30003/30005 根本发不出去。
- 即使删掉这个壳，原生客户端也**进不了战斗**：模块 1500（TowerProxy）的
  `onClimbTowerChallenge` 收到 30004 后只 `sendNt(TowerEvent.TowerChallenge)`，
  而全客户端**没有任何模块监听** `TowerEvent.TowerChallenge`（主包里只有发送方一处）。
  所以必须自己补一条「进战斗」的桥。

### 修法（只动 `web/home-features.js`，服务端一行不改）
1. 接管 `req(1500).default.prototype.sendClimbTowerChallenge`：记下本次要打的层号，
   再调原生发送（保证包体 / 协议号和客户端一致）。
2. 包一层世界数据入口 `World.addMonsterGroup`（模块 `0005`；模块 `0018` 解析 10503 的
   `DATA_MONSTER_GROUP` 块时逐组调它）：收到的组号 == `23000 + 层号` 时，下一帧调
   `World.toBattle(组号)`。

与无限试炼（本文件里的 `World.toBattle(t.groupId)`）同一套做法，也是社区版注释写的
「客户端 `addMonsterGroup` 到这一组时才真正进 `World.toBattle()`」。

### 关键判断：触发条件用「收到塔组」而不是「发过请求」
- 服务端只有**受理**时才把塔组随 10503 下发（`p.towerPendingGroup` → `towerExtraGroups`）；
  被拒（次数用尽 / 未开放）只回 25003 错误提示、不推 10503。
- 组一旦进过客户端 `monsterGroupList` 就**长期留在内存里**（不会被清），所以
  「发过请求就开战」会在「同层已缓存 + 这次被拒」时误进战斗。按收到的组号判定没有这个洞。
- 挂起层号自带 10 秒过期，避免被拒后残留标记被之后的世界数据误触发。

### 两个注入点为什么安全
- `sendClimbTowerChallenge` 是 UI 调用时的**动态属性查找**（模块 1492 的 `onChallenge`
  → `this.proxy.sendClimbTowerChallenge`），原型上的覆盖一定命中。
  （对比坑：`onProto(proto, handler)` 是**初始化时按引用注册**的，改原型对它无效。）
- `addMonsterGroup` 是全类静态，模块 0018 用的就是 `World.addMonsterGroup(o)`。

### 塔面板不用手动关
战斗开始会走原版 `ON_BATTLE_START` → `StartBattleCmd` → `UI.closeAllUI()`
（模块 0523 注册、0526 执行、0001 实现），这就是原版每条战斗入口的收尾方式。

### 验证
- 新增用例「客户端桥接：点「挑战」要真进战斗，塔组基数与服务端一致」：读
  `web/home-features.js`，断言必须有 `World.toBattle(` / `World.addMonsterGroup=` /
  `sendClimbTowerChallenge`，且「挑战和扫荡待补」占位已删净；并把客户端里的
  `TOWER_GROUP_BASE` 数字与 `lib/climb-tower.mjs` 导出的常量对齐（防两边写歪）。
- `tests/climb-tower.test.mjs` 原 13 例 + 新 1 例全过；`npm test` 84 文件 / 586 用例全过，
  新增失败 0；`npm run check` 322 文件 0 错。
- 顺带更正预览弹窗的旧文案：「技能、AI与战斗阵容待补」→
  「塔怪技能与AI待补（只会普攻），编队已可正常开战」。

### 教训
- **「占位补丁」是隐性债**：一个 `Tower[name]=()=>alert(...)` 就把整条协议链掐断了，
  而且它和「服务端已实现」之间没有任何测试报警。改动流水里必须能一眼看到「这里还是壳」。
- 客户端问题的答案常常是「**没有监听者**」：`sendNt(某事件)` 发了不等于有人接。
  查客户端行为要顺着协议常量名读码，确认监听方真的存在（本次 grep 全主包只有发送方一处）。
- 拿不准「服务端受理了没」时，优先找一个**只有成功路径才会出现**的可观察量
  （这里是塔组进 `addMonsterGroup`），而不是「我发过请求」这种本地状态。

# 2026-10-18 · 第 70 版

## 主题：棋盘（太阳神殿/团队副本）打完一场战斗，棋盘必须自己弹回来

### 症状（玩家实测）
太阳神殿里走棋盘 → 走到有事件的格子 → 打赢 → 点掉胜利面板之后：
**棋盘直接消失、人物卡住不能走**，但「背包/人物/宠物」这些按钮点得动。

### 定位：客户端战后流程，服务端没错
进战斗藏一次棋盘、退战斗又藏一次，两次都**不清 `World.escort`**：
- 进：`World.toBattle → BattleProxy.enterBattle → doBattleStart → sendNt(ON_BATTLE_START)`
  `→ StartBattleCmd.exec → World.closeAllUI()`（`clearStack()` + `hideMdr(Layer.window)`）
- 退：`BattleWin.onHide → exitBattle(!0) → sendNt(ON_BATTLE_END)`
  `→ EndBattleCmd.exec → World.showMain()`（`hideTop()` + `clearStack()`）

而 `MyPlayer.isCanMove()`（0031）= `… : !World.isEscortStatus()`，`isEscortStatus()` = `null!=this.escort`，
escort 还在 → 人物永远走不动。（背包等能用，是因为 Main 在 `showMain` 里被重新 showView 了。）

### 为什么服务端补发 14508 救不回来
第 67 版把 14508 改成「12502 回包发完再补发」——但那时玩家还没点「确定」，
棋盘被 showWin 弹出来之后又被 `showMain()` 藏掉；而且棋盘一藏起来，客户端就
**不再发 14511 轮询**（轮询挂在棋盘视图的 update 上），服务端没有别的时机可用。

### 修法：`BattleProxy.exitBattle` 里把棋盘排进 `viewData`
客户端本来就有「战后恢复界面」的开关：`exitBattle` 末尾 `if(t)` 块里，
只要 `this.viewData` 有值就 showWin/showView 回来（原版只用于战斗期间自己弹出来的界面）。
补一句（锚点全包恰好一处，紧跟 `isChangeMap` 复位之后）：
`o.viewData||null==s["default"].getEscort()||null==s["default"].getEscort().pointList||`
`(o.viewData={modName:"Escort",viewType:"EscortNewMain",isWin:!0})`
- 用 `.pointList` 认新版棋盘（0183 的 Escort183 才有；旧版护送 0088 是 moveList/eventList），
  不然会把旧版护送弹成新版棋盘。
- 与对方那份（`%TEMP%\opencode\fxol2` 反编译）唯一差别：补了 `isWin:!0`。对方走 `showView`
  （不压 UISTACK）；而原版开棋盘（14508 → `processEscortStartMsg`）本来就是 `showWin`，
  棋盘在栈上 —— ① 棋盘工具栏开背包/人物时靠 `hideTop/showTop` 收起再弹回；
  ② 离开棋盘（14509 → `showMain` → `hideTop`）也靠栈把棋盘关掉。
- 落点 `lib/client-escort-board-patch.mjs`（`escort-board-showmain-v1` → `escort-board-viewdata-v1`）。

### 为什么不在 `World.showMain` 里补（先写过，弃用）
`showMain` 也能把棋盘弹回来，但一次战斗结束时两处都会 show 一遍棋盘，而
`EscortNewMain.onShow` **不幂等**（`arrayConversion` 会再往 groupBox 塞一套格子按钮、
`addUpdateItem` 再挂一个 1 秒轮询）→ 必须只在一处修。`showMain` 那条更适合
「场景重载（10503）之后 escort 还在」这类非战斗路径，真遇到再按 `viewData` 判重补上。

### 顺手核过、确认没问题的点（免得以后再翻一遍）
- 14508 棋盘包字段序与 `Escort183.fromBytes` 完全一致（含 `short round=passed.size-1`、
  `byte turnType=1`（FAVOURER）、`byte 战力对数`）。
- 14511 刷新包：`byte status(0)` `byte 奖励数(0)` `byte escortType(1=NEW)` `byte pos`
  `int nextMoveTime` `int nextOverTime` `short round` `bool hasRob(0)` `byte 图标数(0)`
  → `Escort183.processEscrotRefreshPosMsg` ✓。
- 14511 结束包：`byte status(1)` `byte 奖励数(0)` `bool 有无奖励块(0)` `byte 原因(0)`
  `string 文案`（escortType=FAVOURER 才读）`byte u(0)`，之后接**数据块**
  `int mapId, byte x, byte y, int flags(0)` → `processEscostEndMsg` + `processDataBlockFlagMsg` ✓。
  （`processDataBlockFlagMsg` 口径是「先 mapId、再 x/y、再 flags」；map 262 不在镜像/城市/国家
  分配段（30000/10000/20000 起），所以不会多读一个 `short orgMap`。）14509 离开包同一口径 ✓。
- 棋盘进度（`pos`/`passed`/`completed`/`solarDone`）与存档恢复链（`handleSolarChallenge` 的会话恢复、
  `settleSolarBattle` 用 `board.pos` 记「这格通过」）自洽；**「打赢了但进度不对」暂未找到确定性
  服务端 BUG** —— 玩家是在棋盘不可见的状态下报的，倾向与「棋盘消失」同源，待上机复验。
- 对方那份 `team-dungeon-service.mjs` 与我们的实现逐字等价，**同样有这个 bug**
  （它的客户端是直接改主包，我们这边按补丁链打）。

### 验证
- `tests/client-patch-chain.test.mjs`：主包长度断言 `4565616 → 4565641`（本补丁 +152），
  escortBoard 用例改成断言 `viewData` 注入 + `isWin:!0` + 幂等；`node --test` 12/12 过。
- `npm test` / `npm run check`：新增失败 0（结论见提交说明）。
- **上机复验通过**（用户 2026-10-18 报「太阳神殿副本已成功修复」）：棋盘打完会自己弹回来、
  人物能继续走。之前那批「进度不对」的反馈按同源处理，未再复现。

### 教训
- **「窗口被藏了、会话状态没清」是一类固定症状**：`closeAllUI/showMain` 只动窗口不动 escort，
  卡住的是 `isCanMove()`。以后见到「UI 没了但别的功能还在」，先查「谁藏了窗口、谁本该把它弹回来」。
- **客户端自带的开关优先于新写逻辑**：`viewData` 是原版就有的战后恢复机制，塞进去比在 `showMain`
  里自己 show 更贴原版，也避开了「onShow 不幂等」的坑。
- 对照另一份实现的反编译产物时，要按「同一逻辑」翻译，别照抄没被验证的分支
  （`showView` vs `showWin` 这种差别会连带影响 UISTACK 行为）。

# 2026-10-18 · 第 71 版

## 主题：城市/玛雅小补丁 —— 任务公告板可见位、市长对白、飞行驿站航线、城市升级任务判定、玛雅旧任务归档

移植「幻想世界OL 2.0 新版」本批清单里的第三项（前两项是团队副本/太阳神殿、永泽塔挑战）。
对方三个模块：`city-template-fixes.mjs`（90 行）、`city-progress.mjs`、`maya-progress.mjs`；
我们按本工程的习惯重写（先读回校验、重建必须逐字节相同、缺项告警不抛错），并补上调用点与测试。

### 1. 任务公告板在自己城市里根本看不见（真 BUG）
主包 `ModelConst`（偏移 ~1147619）里状态字节的语义是**逐字核对过**的：
`STATUS_VISIBLE=1`、`STATUS_ENABLE=2`、`STATUS_PASSABLE=4`、`STATUS_MISSION_DATA_USE=8`、
`STATUS_MISSION_LOAD_EVERY_TIME=16`、`STATUS_JUMP_ICON=32`、`STATUS_HIDE_PLAYER=64`、
`STATUS_GUIDE_NPC=128`、`STATUS_INIT_VISIBLE=1024`、`STATUS_INIT_ENABLE=2048`。
个人城市里「日常任务列表 / 日常高级任务列表」（1000:6、3090:6、3090:8）录到时 `status=2` ——
**只有「可交互」没有「可见」**，所以玩家在自己城市里看不到任务板；本工程 `npcEnabled()` 的
`(status&3)===3` 也正是同一个口径（对照 tests/memorial-npcs.test.mjs：「type 0 的展示状态位是
原版既定的 23」= 1+2+4+16）。补上可见位 → 3，与录制里 183 个正常 type 0 NPC 一致；
活跃度面板里那条「日常任务列表」寻路（14551 就是奔 1000:6 去的，见 lib/daily-service.mjs）也终于到位。

### 2. 市长还在说「这是一座新生的城市」
7 号「代理市长-雷恩」（`missionData=[3005,1,0,0]`）是**城市五级扩建完成后才会出现**的那位
（客户端按 missionData 位放行可见性），对白却还是扩建前版本 → 换成扩建后文案；
扩建前那位（`missionData=[0,0,3005,1]`）保持原样。原对白留在 `recordedTalkDetail`。

### 3. 飞行驿站只有 5 条原版航线
驿站招呼语自己写着「可以快捷的前往各个主要的城市，原有的冒险地图跳转可通过圣域、紫禁城等
各大城市前往」，菜单却只有太阳城/新月古镇/圣域/紫禁城/英雄挑战赛。按【主城】【地区】【副本】
【节日】四组补齐 **60 条**航线（9+14+24+13，对方那份是同一批号码）。
- 落点一律取目标地图自己的 `spawn`；`jumpMapReqMissionID=0` 无门槛（与 applyOpenPortals 同思路）。
- 目标只做静态校验：已采集、不是个人城市模板、出生点能塞进 byte/short；缺项**告警跳过**
  （这份补丁在 `official-data.ensure()` 里跑，抛错等于起不来服务）。
- 记录布局按客户端 `readPowerNPCData` 逐字段核对：14 头 + 名字/招呼/对话 + 状态/朝向/x/y/范围x/范围y
  + [missionData 6 字节：仅当 状态&8] + 传送菜单(byte 计数){菜单名(utf) 地图(short) x(byte) y(byte)
  需求任务(short) 需求状态(byte)} + 战斗/商店/导师三段。**先用解析结果原样重建一次，与原件逐字节相同**
  才敢改（`tests/city-template-fixes.test.mjs` 再用客户端自己的解码器 `Npc.fromBytes` 读回来比对）。
- 65 项菜单是原版最长的（录制里传送门最多 5 项）：客户端 power-NPC 菜单与系统菜单共用同一套
  可滚动列表（`Tool.addChoiceMenu`），所以能滚；但这是本补丁里最需要上机看一眼的点。
- 注入点排在 `official-data.ensure()` 里**所有补地图的补丁之后、建索引之前**（航线目的地要在地图表里，
  而 NPC wire 直接从 official.maps 取）；又因为晚于 `applyOpenPortals`，驿站原有 5 条的门槛
  此时已被放行，读回来照样通过校验、不会被改回去。

### 4. 城市升级任务（3002—3005）：完成记录被跨天清掉，等级却留着 → 任务卡死
本工程的任务完成判定是「`quests.completed` 里有这个 id」，而 `ensureDaily()` 跨天会把**非新手任务**
从 completed 里清掉（刻意的：跨天重开天然成立，见 lib/replayable-chains.mjs）。3002—3005 的 setting
（288/800）没有每日位，于是第二天：城市等级还在（`p.city.level` 是持久字段），升级任务却「没完成过」→
公告板/市长又把它们摆出来 → 玩家接了就**卡住**（`applyCityMission()` 会以「城市等级已变化，请重新
查看任务。」拒绝交付，任务也退不掉）；所有「前置是升级到 N 级城市」（acceptCondition type 9）的任务
还会一起变成不可接。
修法（`lib/city-progress.mjs`）：城市等级本身就是完成证据 —— `level >= id-3000` 即算完成。
挂三处：`daily-activity.missionDone()`（判定入口，连带 `missionClosed`/`missionsAt`/`npcEnabled`/
`officialSign`/条件 type 9 全部受益）、跨天重置的 completed 过滤（把升级任务留下）、
`game-packets.missionBits()`（客户端任务位图并上 `completedCityUpgrades(p)`）。
**注意**：`city-progress.mjs` 刻意不 import `city-state.mjs`（那会经 official-data 绕成循环），
等级默认值 1 与 `cityState()` 保持一致。

### 5. 玛雅旧任务（3220—3226、1823）归档
8700—8709 十环取代了原版 3219→3220→…→1823→1824；这些旧号在我们这份 official-v305 里**一条都没
采集到**（`officialMissions.has(3220)===false`），本地又把 1824 的前置改成 8709、838 蒂卡尔可见性
前置改成 3219（lib/maya-continuation.mjs）。于是**从正式服导出的存档**里它们会一直挂在
`quests.active` 里（任务栏看不到，但接取/交付判定还数着）。`lib/maya-progress.mjs` 命中就把它们
整块挪进 `p.mayaRetiredProgress`（revision 沿用对方的 `restore-20260926-palace-v1`）再删除，

调用点在 `restoration.normalizeRestoration()`，紧跟 `migrateCaptured81Progress()`。

  多出 6 字节 missionData（`STATUS_MISSION_DATA_USE`）与本地 type 0 用 23 的原因。

#### 教训
- **`INITIAL_*` 这类「初始值常量」不要当上限用**（`Math.min(INITIAL_X, …)`）：加「扩容」功能时
  它会把效果悄悄吃掉，而且看起来一切正常（只有提示、没有实际变化）。
- **「不在白名单里」≠「会隐藏」**：原版主界面按钮的可见性由原版代码决定，想让它消失必须
  进强制隐藏名单。
- 摘掉 UI 元素要**连每 1 秒刷新的 `disabled` 循环一起摘**（`web/offline.js` 那两处），
  否则元素没了、定时器还在 `getElementById(...).disabled` 上崩。
- 客户端「提示类」补丁优先动**节奏与队列长度**（显示层），不要碰提示的产生方 ——
  这样战斗数值/协议一个字节都不用动。
