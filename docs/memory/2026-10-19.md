# 2026-10-19 · 第 77 版：英雄图鉴真正可用 +「点亮所有图鉴」道具

> 前一天的日志见 `2026-10-18.md`（第 69—76 版）。这一版开始按用户给的 6 项需求清单
> 逐项对齐参考实现「幻想世界OL 3.0 最终版」；本版做的是清单第 ① 项
> （图鉴全亮 + 新增消耗品「点亮所有图鉴」），顺序是 ③ → ④ → ① → ② → ⑤ → ⑥。

## 一、动机

用户要的是：**图鉴（收集系统）能真正用起来** —— 打开面板看得到收集率 / 等级 / 加成说明，
「点亮」点得动；再给一件消耗品「点亮所有图鉴」，一键全亮并**立刻**拿到加成。

参考实现那一侧的做法是**纯客户端 hack**（`client/worldol-handbook-lit.js`：hook
`RaidersProxy.onHandBookInfo`，看到 localStorage 标志就把回来的 `itemInfos` 全部置
`unlock=true`、rate 拉满，再在 `fixBook()` 里把 `BookGroupModel.bookGroupPower` 整份
重算成自己那张表）。它没有服务端，所以加成就只是「面板好看」。
本工程是服务端权威的（战斗走 12501 → `context.battle` → `nativeCharacterStats`），
所以要**做得更实**：状态、等级、加成都落服务端，客户端只镜像。

## 二、根因：为什么以前是死的

原版客户端的图鉴链路（主包模块 0179 BookGroupModel / 1150 主页 / 1154 等级 / 1157 点亮）：

| 方向 | 协议 | 客户端行为 |
| --- | --- | --- |
| C2S | 32101 `C2S_HAND_BOOK_INFO` | 只发 group+type |
| S2C | 32102 `s2c_HandBookInfo` | `nowBookGroup=...` → 面板按 `info.level` / `info.rate` / `info.power>0` / `canUnlock` 画 |
| C2S | 32103 `C2S_HAND_BOOK_UNLOCK` | `sendHandBookUnlock(group,type)`，**没有 itemIds** |
| S2C | 32104 `s2c_HandBookUnlock` | `canUnlock=false`，按 itemIds 把 `itemInfos[].unlock=true`，更新 level/rate |
| S2C | 32109 `s2c_HandBookPowerInfo` | 清空静态 `BookGroupModel.bookGroupPower`，再把每条 `effect` 为真的 `powerValue` 累加到 `bookGroupPower[power]` |

我们以前只回 32102（一页一条、全部 `unlock=false`、rate/level 全 0），32103 直接提示
「单机图鉴可查阅；点亮和幻化养成尚未接入」，32109 从来没发过 —— 于是面板永远全黑、
`canUnlock=false`（点亮按钮不显示）、加成恒为 0。

## 三、做法

### 1. `lib/handbook.mjs`（规则层，只 import `official-data.mjs`）

* **页索引**：抓包目录 `official.catalog`（2240 条）按 `sources[].group/type` 分页，得到
  32 页（`1:13..39` / `2:0..12` / `3:7·8·9·41` / `11:11`），页内按 itemId 去重。
  语义与原来的 `handbookPage` 完全一致（tests/official.test.mjs 的「一条不落」照旧）。
* **收集率 → 等级**：`Math.round(rate/100*70)`，100% = 70 级；0% = 0 级。
* **四张加成表**（照抄参考实现 `getGroupBonus`，档位 ≥70·≥60·≥50·≥40·≥30·≥20·≥10·其余）：
  * 宠物 `[7,8,9,41]`：`[2,4,6,8,10,89..96,232]` 各 +100/80/60/50/40/30/20/10；
  * 坐骑 `11`：`57`（致命点）/`173`（无视伤害减免）= 700…50，`130`（攻击次数）= 7…1；
  * 特殊 `[19,24,34,37,39]`：`171`/`169` = 1000…50，`56` = 500…20；
  * 其余（普通武器防具）：`58`/`59`/`60` = 500…50，`141`（全武器伤害、耐久%）= 20…1。
* 导出 `handbookView` / `unlockHandbookPage` / `unlockOwnedItems` / `refreshHandbook` /
  `lightAllHandbook` / `handbookBonus` / `handbookLevel`。

### 2. 存档字段与「谁是唯一真源」

```
p.handbook = {
  unlocked: {"1:13": [条目编号…]},   // 玩家点亮过什么（唯一真源）
  lit: false,                        // 用过「点亮所有图鉴」
  powers: {"58": 9500, …}            // 派生缓存：加成合计
}
```

`powers` 是算出来的，每次状态变化 + 每次进世界都 `refreshHandbook()` 重算 ——
好处是换一张加成表，老存档下次登录就能生效；同时 `native-character-stats.mjs`
读它时**不需要 import handbook**（`native-character-stats ↔ restoration` 已经是循环，
再挂一手容易出意外）。

### 3. 协议接线（`lib/official-service.mjs`）

* `32101` → `32102`：带角色时给真实 `unlock / level / rate / canUnlock`，`power=1`
  （客户端 `updatePage` 用 `info.power>0` 判断「暂未开放」，power=0 就整页灰掉）。
  不带角色时保持「全未点亮 / canUnlock=false」的纯目录视图（既有契约）。
* `32103` → `32104`（整页条目编号 + 新 level/rate）+ `32109`（新加成）+ `store.save()`。
* `handbookPage(1,13,role)` 会自动点亮？**不会** —— 32101 是查询，一行都不写角色（见下面教训）。

### 4. 加成落地（`lib/native-character-stats.mjs`）

原版 `Model.getSkillPowerValue(type,key)` 的第一段就是 `this.getPower(key)`，而
`getPower` 里写着 `t += RoleGodData.getPower(...)` 与 `t += BookGroupModel.getBookGroupPower(...)`。
服务端对应的桩是：

```js
getSkillPowerValue:(type,key)=>key>0?((type===1?(powers.get(key)||0):0)+(featurePowers.get(key)||0)+(bookPowers.get(key)||0)):0
```

即图鉴加成与特征加成（`featurePowers`）同一层、同样不按技能类型过滤 —— 这是
「面板显示」与「服务端战斗」用同一个数的地方，对不上的话就是「面板写 +500、实际加 50」。

### 5. 「点亮所有图鉴」道具

* 定义在 `lib/handbook-item.mjs`（单独一个模块，避免 `official-data → handbook` 互相 import）：
  `id=800110`、`type=28`、无 power、`stackNum=99`。
  注册点在 `lib/official-data.mjs` 的 `ensure()` 里（和 `localEnchantments` 同一处，
  必须**在索引 Map 建立之前**）；编号常量在 `lib/local-items.mjs`，
  并进 `PINNED_SUPPLY_ITEM_IDS`（补给商人 · 消耗品分类最前面，免费领）。
* 为什么等待类型是 `BAG_NO_WAIT(0)`：客户端 `createPlayerBagMessage` 上游那段
  `b=BAG_NO_WAIT` 的分支 —— 无 power 的 type 28 道具既不是药、也不是孵化/宝箱/绑定，
  于是 `b` 保持初值 0。客户端对 `BAG_NO_WAIT` 就是 `sendProto` + 本地自己扣一件、**不等回包**。
* 服务端在 `lib/restoration-service.mjs` 的 `12001/action3` 里按 `itemId` 提前认领
  （在 `jobBooks` / 药水兜底之前）：校验 `waitType===0`、`quantity>0` → `consumeItem` →
  `lightAllHandbook`（`lit=true`）→ `store.save()` → 推 `32109` + 公告 `10509`；
  失败时按既有写法把角色还原（`Object.assign(p,before)`）。

### 6. 客户端文案（`web/offline.js`）

原版 `getGroupTypeDes(group,type,level)` 靠 `getPowerDesc(info.power, info.powerValue + info.addValue*档位)`
—— 一次只描述得出来**一条**属性，而图鉴每一档都是好几条一起加（宠物全属性 + 宠物伤害、
坐骑致命点 + 无视伤害减免 + 攻击次数…）。所以整段覆盖成参考实现那张字符串表，
档位阈值与加成表一一对应；`level<=0` 仍返回「无」（照原版）。

> `web/*.js` 是静态资源：电脑版直接加载 `web/offline.js`，APK 由
> `安卓打包/standalone/build.mjs` 把 `web/` 平铺到站点根 —— 所以**不用**两边挂补丁，
> 也不进 `client-patch-chain`（那条链只用于主包 `fff570bb….js` 的字符串补丁）。

## 五、教训（这一版真正踩到的）

1. **32109 只许发一组合计值**。第一版我按 `handbookGroups().infos`（4 组）各发了一份同样的
   加成表，想着「组是给客户端看的」。实际上 `onHandBookPowerInfo` 会把**所有** info 的
   `powerValue` 累加进同一个静态 map（`group` 那一位它根本不读）→ 客户端把加成乘了 4 倍。
   测试里当场抓到（`38000 !== 9500`）。改成单组（`group=0`）后两边一致。
2. **道具定义字节的尾巴是条件写的**。原版 `Item.fromBytesAtts2` 的 type 28 分支：
   `power1/powerValue1/power2/powerValue2/vipLevelReq` 之后，**只有 `power1===181`（附魔卡）
   才继续读 `power3/powerValue3`**，然后才是 `needShowRate`。我照 `enchantment-data.mjs`
   的 Writer 链写全了三对 power，于是解码器多出 4 个字节读不掉
   （`Reader.finish()` 报 `Unconsumed bytes 4 at 113`）。无 power 的道具必须少写那两项。
3. **查询类接口不许改角色**。第一版 `handbookState(p)` 是「取（必要时创建）」，
   32101 只是查询却把 `p.handbook={unlocked:{},lit:false}` 挂到了角色上 —— 测试的
   `assert.deepEqual(p,before)` 立刻红。现在拆成两只手：
   * `handbookState(p)`：**只读**，老存档 / 没打开过图鉴的角色拿到一个不进存档的空壳；
   * `ensureHandbookState(p)`：写路径（点亮 / 道具 / 进世界重算）才用。
   （AGENTS「查询类接口不许改角色」这条又一次救了场。）
4. **`protobufSchemas` 只认 `switch` 形态的生成代码**。单条件（`t>>>3==1 ? …: skip`）解不出来，
   得在 `tools/capture-decoders.mjs` 里手写 schema —— 已有 `s2c_HandBookGroupList` 的先例。
5. 加成确实很大（全亮后普通页 19 页 × `58:500` 起，`ATK_STR_NEARBY` 能到五位数）。
   这是参考实现的原样数值，本版**不改**；要调就地改 `BONUS_TABLES`（客户端文案表要同步，
   测试会逐档对数字）。

## 一、动机

我们有 90019（快照）/90020（动作）两个号 + 一个自画的下拉面板，能打、能领奖，
但**界面不是原版的**：原版客户端自带一整套「无限试炼」窗口
（`analysis/modules/1472.js` FinalBossProxy / `1473.js` FinalBossMdr 主界面 /
`1475.js` 编队 / `1477.js` 玩家信息 / `1479.js` 排行榜 / `1481.js` 挑战记录 /
`0146.js` FinalBossData / `0338`Top3Item `0339`FinalBossRankItem `0340`FinalBossRecordItem），
它靠一串我们没接的协议驱动：

| 方向 | 协议 | 客户端行为 |
| --- | --- | --- |
| C2S/S2C | `C2S_FINAL_BOSS_INFO` / `S2C_FINAL_BOSS_INFO` | `applyFinalBossInfo()` → `_data.finalBossInfo` → `updateView()` |
| C2S | `C2S_FINAL_BOSS_CHALLENGE` | `applyChallenge()`：次数够就发请求 |
| C2S/S2C | `C2S_FINAL_BOSS_BUY_TIMES` | `applyBuyTimes()`：`lessBuyTimes<=0` 先 Tips，否则二次确认后发请求 |
| C2S/S2C | `C2S_FINAL_BOSS_PET_SET` | `applySetPets()`：把 `_data.petsConfig`（= `finalBossInfo.petIds`）发上去 |
| C2S/S2C | `C2S_FINAL_BOSS_RANK_INFO` / `C2S_FINAL_BOSS_RECORD` | 排行榜 / 挑战记录两页 |

所以本版的思路和参考实现一致：**不要去改客户端 UI，而是把本地数据喂进原版门面、
把那几个要发协议的方法整个换成本地动作。**

## 二、服务端（规则层）

`lib/trial-challenge.mjs`：

## 三、修掉一个真实 bug（上一版留下的）

旧 `settleTrialBattleAndNotify` 用 `p.trialPendingGroup===TRIAL_GROUP_ID` 当「这一场是不是
我们下发的」判据，可 `lib/game-service.mjs` 的 12501 受理时**已经** `delete p.trialPendingGroup`
（跟永泽塔塔组同款清理）→ 12502 时 `pending` 恒 false → **实战里那次「自动结算」永远不会发奖**；
单测因为直接调 `settleTrialBattleAndNotify(p,2,send,now)` 才一直是绿的。
现在结算只看胜负（+ 上报伤害），不再依赖这个标记，并补了「同一场不允许二次结算」的断言。

## 五、坑（都是读原版码换来的结论）

1. **`onShow` 一定会 await `applyFinalBossInfo()`**：它必须一起换掉，否则那次
   （我们没实现的）协议回包会把塞进去的 `finalBossInfo` 冲掉 —— 表现是「界面开了但全是空的」。
2. **编队里的宠物 id 只能是宠物模型上的真 Long**：`addPet`/`delPet`/`isPetSelected` 都对它调
   `.eq()`，字符串进去当场 `TypeError`（`o.eq is not a function`）。所以存档里存字符串，
   `buildTrialInfo` 用 `trialPetRefs()` 经宠物代理 `getMyPetById()` 换回真 Long。
   （`updatePetList` 也走同一个函数，两侧一致才点得动。）
3. **排行榜条目 `rank` 是 0 基**（`0339` 里 `n=i.rank+1`，`n<=0` 走「未上榜」渲染），
   而参考实现写成 `rank=i2+1` 是错的（会显示第 2、3…）。我们按数组下标给。另外 `1479`
   在列表里找不到自己会去 `new pb.FinalBossRankInfo` —— 本工程**没有 `pb` 全局**，
   所以 `trialRankRows()` 一律把玩家那行补进列表，让原版走 early-return 分支。
4. **假 Long 够用**：`Tool.getHeadIcon2` / `Tool.getJobByIcon1` 只调 `.toNumber()`，
   所以 `icon1` 给 `{toNumber:()=>n}` 即可（`window.Long` 虽然存在，但没必要引入）。
   奖励格（`0086` ItemIconNameC）要 `getIsItemPetEquip`/`isVipItem`/`getIconString`/
   `getNameInfo`/`grade`（`grade` 是品质底图下标，只能是 0..6）+ 点击时的 `doViewItem()`
   （它发 12016，本工程已实现）。名字长的道具在实机奖励格里会空白，所以留了短名表。
5. **「+」按钮不要重绑**：原版 `onTapBuyTimes` 自己会调 `this._proxy.applyBuyTimes()`，
   而那个方法已经被我们换成 90020 的本地动作；再 `listen` 一次就是一次点击买两次
   （`Mdr.listen` 只是 `onEgret(target,type,fn,this)`，egret 允许重复监听，不查重）。
   原版「还有剩余次数就先 Tips」的行为照抄保留。
6. `web/*.js` 是静态资源（电脑版直接加载、APK 由 `standalone/build.mjs` 平铺 `web/`），
   所以**不用两边挂补丁**，也不进 `client-patch-chain`（那条链只给主包打字符串补丁）。

## 二、真缺口：一个怪物 id 装了两份属性（困难塔复用普通塔的怪）

* 普通塔 1—120 层与困难塔 121—132 层**共用同一批 id（2700–3000）**：困难塔那份属性整表 ×7

* 编队 wire 与模型包都是**按 id 认怪**，一个 id 只能带一份属性 → 第二份必须换号。
  参考实现没修（他们那份也是「同 id 只收第一份」），所以困难塔实际下发的是普通塔的弱属性，

  * `towerMonsterSignature(monster)`：除 `wireBase64`/`sources`/`localTowerVariantOf` 之外的全部字段
    （含 id）组成签名。签名相同 → 复用同一个 id；签名不同（同 id 两份属性）→ 换本地号。
  * `LOCAL_TOWER_VARIANT_BASE=21000` 起递增：官方怪物 id 最大 4071，20000–32767 在本工程无占用，
    上限取 32767 是因为**编队 wire 的怪物槽位是 short**。

    （重写过属性区就等着解码器报错）。
  * `registerClimbTower()` 里把换过号的：并进 `officialMonsters`（`sources:[{origin:'climb-tower',variantOf:原id}]`）
    并把该层的编队槽位、模型包都指向新号；对外只经 `towerFloorMonsterIds(floorId)` 暴露。
  * 返回值多一个 `variants` 计数，`/api/status` 能看到。
* 实测：132 层 / 271 条记录 / 160 个唯一 id / **27 个换号变体**（28 个重复 id，其中 2731

## 五、坑

1. **一个 id 两份属性时，模型包与编队必须用同一个新号**：只换编队不换模型包（或反过来）会表现为
   「怪物是对的但属性是另一个」——两者都从 `towerFloorMonsterIds()` 取，别各写一份。
2. **换号只改 wire 头 4 字节**：塔怪 wire 是「3 字节长度 + UTF-16BE 名字」那套（不是 `Reader.utf()`），
   重写属性区必乱码。
3. **`openFloor=0` 不能被兜成 1**：`Number(x)||1` 这类写法会把「无前置」变成「第 1 层永远开不了」，
   与第 73 版 `bagCapacity` 同一个坑（`INITIAL_*` 当上限）。
4. **傲雪凌霜礼盒（100781）仍然打不开**：本工程没有 type 28 的开箱机制
   （`restoration-service.mjs` 只特判 800110/288/42000/40005）。参考实现有 `custom-gift-boxes.json`
   + `openContainer()`（45 个盒子、含 100781 的表，内容是他们**自己配的**：官网文案说的是
   「1% 放逐之刃 / 1% 波板糖 / 98% 日常消耗品」，与他们那份配置并不一致）。
   本版不搬开箱（那是另一个子系统），因此礼盒目前只能当收藏 —— 与参考实现同样处境。
   扫荡卷（5300）不受影响：它本来就在补给商人「消耗品」里免费领。
5. **单机面板顺带说明**：`web/home-features.js` 的塔页加了一行文字说明「全层开放 + 奖励统一」，
   `web/*.js` 是静态资源、不用两边挂补丁、也不进 `client-patch-chain`。

# 第 80 版：图鉴加成整块删除（修掉「宠物战斗状态不完整 → 奖励全不发」）

> 用户报障：第 77 版（图鉴）之后，角色**每场战斗打完**都提示

## 一、根因（客户端码 + 用户存档逐条对上）

* 客户端 `onHandBookPowerInfo`（主包偏移 ≈3744996）：
  `BookGroupModel.bookGroupPower={}` → 遍历 `infos[].info[]`，**只有 `info.effect` 为真**才
  `bookGroupPower[info.power]+=info.powerValue`。
* 战斗单位 `getPower(key)` = `RoleGodData.getPower(...) + BookGroupModel.getBookGroupPower(...)`
  （仅 `TYPE_PLAYER`）—— 所以 32109 发的值直接进了战斗单位的「能力值」：
  角色面板的出手/魔攻、战斗公式、以及**宠物属性**（主人侧能力号 89–96 就是宠物百分比能力）
  全都被带着走。
* 我们第 77 版发的合计（用户存档里角色 1004「扣蓝」的 `p.handbook.powers`）：
  `57:50`（坐骑表 → **攻击次数 +50**）、`58/59/60:600`（普通表 → **物攻/魔攻/武器伤害 +600**）、

* 宠物血蓝对不上：服务端 `petAttributes` 用的是存档里的旧快照 / 装备+技能 powers（**不含**图鉴），

  12502 的 `petHP>max.hp` 判定因此**每一场**都命中 → `context.battle` 搬进 `rejectedBattle`
  → 「未发放奖励」，而且背包/人物/宠物面板都正常，看着像随机故障。
* ⚠ 顺手**纠正第 77 版文档里一条错误结论**：那条「按组重复发同一份 = 加成乘上组数」是错的
  —— 客户端每个包都先 `bookGroupPower={}` 清空。真正要记住的是 `effect` 为真才累加、

## 五、教训

1. **「服务端说加多少」这种全局能力值，破坏力是全方位的**：同一份 powers 既进属性面板、
   又进战斗公式、还会通过主人侧能力号影响宠物 —— 一个数字对不上就能让**每场**结算被拒。
   以后再加这类全局增益，先在「宠物/军团」这类**跨实体派生**的地方验一遍。
2. **客户端的加点是权威落点**：原版是 `getPower = god + book`，我们折进 `getSkillPowerValue`
   等于把同一份加成放在更靠前的位置，量级会随调用点重复放大（第 77 版就是这么「变态」的）。
3. **空包也是一种指令**：客户端收到空 32109 会清空自己的加分表，所以「删功能」不需要客户端补丁，
   老存档也能自动回滚 —— 比让玩家清缓存/重装省事得多。
4. **测试要钉住「没有加成」这件事**：属性不变的断言 + 文案里不许出现数字，两道守卫才能防止
   将来手滑把加成加回去（第 77 版的测试当时只钉了「加成等于多少」）。

# 第 81 版：图鉴点条目能看道具详情（12016 回包少了一个状态字节）

## 一、问题与根因（读客户端码换来的结论）

用户：「图鉴里的任意选项，点进去应该可以显示装备的属性、技能啥的，跟在背包里的展示的应该
要一样……现在空有图鉴而没有道具详情。」

客户端 1150（图鉴主页）的 `tapItemSelect` 是**两跳**：

1. `createBookItemInfo(编号)`（模块 1147）→ `CG_HAND_BOOK_ITEM_INFO`(16051)，回包就是这件
   道具的**定义字节**，客户端直接 `Item.fromBytesAtts2` 解析。这一跳一直是对的：目录里的
   `definitionBase64` 本来就是从抓包里**同一条协议**的应答导出的
   （`tools/catalog-core.mjs` 的 `request({kind:'item'})` 打的就是 16051）。
2. `Tool.alertItemInfo(编号)`（模块 0001）→ `Item.getItemUseId(编号)`（模块 0032）→
   `CG_ITEMTYPE_GETINFO`(12016) —— 这是「查看一件**我没有**的道具」的通用接口
   （首充预览、奖励格 `doViewItem` 都走它），拿到定义后才 `checkItem(item)` 弹详情窗。

根因在第二跳的**回包形状**：客户端模块 0035 的 `Tool.sendProtoAsync` 里有一张
`resultMsg` 名单（167 条协议），名单里的协议**回包必须以状态字节开头**：

```js
e.resultMsg.has(r) ? (n = a["default"].processMessage(o, i)) : a["default"].setMsgTag(r, o)
// processMessage: var b = t.getByte(); return 0 > b ? (alertMessageGuide(t.getString(), i), !1) : (setMsgTag(...), !0)
```

- `CG_ITEMTYPE_GETINFO`(12016) **在**名单里；`CG_HAND_BOOK_ITEM_INFO`(16051) **不在**。
- 所以 12016 的正确回包 = `byte(0)` + 定义 + `byte(套装组数)`
  （`Item.getItemUseId` 解析完定义还会接着调 `Tool.processGetSuitInfoMsg`，读一个「组数」计数）。
- 第 77 版写的是「定义 + 一个 0」：**开头少一个状态字节**，末尾那个 0 本来当套装组数用。
  于是客户端把定义的第一个字节（道具类型，例如 13）当状态字节读掉（正数 → 不报错、静默通过），
  再从第二个字节开始解析定义 → 抛 `Truncated at 10, need 4396` → 被 `getItemUseId` 里的
  `catch` 吞掉（只 `console.error`）→ 返回 undefined → `checkItem(undefined)` →
  界面上**一点反应都没有**。

用客户端自己的解码器（`tools/capture-decoders.mjs` 的 `Item.fromBytesAtts2`）模拟两种回包，
结论与推断完全一致：旧回包抛 Truncated，新回包 id/name/type/剩余字节全部正确。

## 二、改法（客户端一行都不用改）

- 顺手把「目录里没有定义」时的旧行为（`return false` 不认账 → 客户端白等 10 秒
  `sendProtoAsync` 超时、抛出没人接的 rejection）改成回 `byte(-1)` + 一句文案，

## 四、教训

1. **「客户端不认识的回包」和「客户端读错位的回包」症状一样**：都是「点了没反应」。
   以后再碰到「某个界面点开是空的」，先查一眼这个协议在不在客户端 `resultMsg` 名单里、
   后面还要不要读别的尾巴字段（套装组数就是一个），比猜业务逻辑快得多。
2. **静默 catch 会把 bug 藏起来**：`getItemUseId` 用 `try{...}catch{console.error}` 包住解析，
   解析失败只是 `return undefined`，界面毫无提示。所以这类「查看类」接口要按**客户端的读法
   逐字节**验，不能只验「服务端发出去了字节」。
3. 同类接口还没系统核过：凡是「查看一件道具/宠物/怪物」的通用接口，回包形状都要按
   客户端 `resultMsg` + 后续读取函数来定。这次只核了 12016（图鉴/首充/奖励格共用的那条）。
