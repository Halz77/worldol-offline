# 2026-10-19 · 第 77 版：英雄图鉴真正可用 +「点亮所有图鉴」道具

> 前一天的日志见 `2026-10-18.md`（第 69—76 版）。这一版开始按用户给的 6 项需求清单
> 逐项对齐参考实现「幻想世界OL 3.0 最终版」；本版做的是清单第 ① 项
> （图鉴全亮 + 新增消耗品「点亮所有图鉴」），顺序是 ③ → ④ → ① → ② → ⑤ → ⑥。

## 一、动机

用户要的是：**图鉴（收集系统）能真正用起来** —— 打开面板看得到收集率 / 等级 / 加成说明，
「点亮」点得动；再给一件消耗品「点亮所有图鉴」，一键全亮并**立刻**拿到加成。

参考实现那一侧的做法是**纯客户端 hack**（`client/worldol-handbook-lit.js`：hook
`RaidersProxy.onHandBookInfo`，看到 localStorage 标志就把回来的 `itemInfos` 全部置
`unlock=true`、rate 拉满，再在 `fixBook()` 里把 `BookGroupModel.bookGroupPower` 整份
重算成自己那张表）。它没有服务端，所以加成就只是「面板好看」。
本工程是服务端权威的（战斗走 12501 → `context.battle` → `nativeCharacterStats`），
所以要**做得更实**：状态、等级、加成都落服务端，客户端只镜像。

## 二、根因：为什么以前是死的

原版客户端的图鉴链路（主包模块 0179 BookGroupModel / 1150 主页 / 1154 等级 / 1157 点亮）：

| 方向 | 协议 | 客户端行为 |
| --- | --- | --- |
| C2S | 32101 `C2S_HAND_BOOK_INFO` | 只发 group+type |
| S2C | 32102 `s2c_HandBookInfo` | `nowBookGroup=...` → 面板按 `info.level` / `info.rate` / `info.power>0` / `canUnlock` 画 |
| C2S | 32103 `C2S_HAND_BOOK_UNLOCK` | `sendHandBookUnlock(group,type)`，**没有 itemIds** |
| S2C | 32104 `s2c_HandBookUnlock` | `canUnlock=false`，按 itemIds 把 `itemInfos[].unlock=true`，更新 level/rate |
| S2C | 32109 `s2c_HandBookPowerInfo` | 清空静态 `BookGroupModel.bookGroupPower`，再把每条 `effect` 为真的 `powerValue` 累加到 `bookGroupPower[power]` |

我们以前只回 32102（一页一条、全部 `unlock=false`、rate/level 全 0），32103 直接提示
「单机图鉴可查阅；点亮和幻化养成尚未接入」，32109 从来没发过 —— 于是面板永远全黑、
`canUnlock=false`（点亮按钮不显示）、加成恒为 0。

## 三、做法

### 1. `lib/handbook.mjs`（规则层，只 import `official-data.mjs`）

* **页索引**：抓包目录 `official.catalog`（2240 条）按 `sources[].group/type` 分页，得到
  32 页（`1:13..39` / `2:0..12` / `3:7·8·9·41` / `11:11`），页内按 itemId 去重。
  语义与原来的 `handbookPage` 完全一致（tests/official.test.mjs 的「一条不落」照旧）。
* **收集率 → 等级**：`Math.round(rate/100*70)`，100% = 70 级；0% = 0 级。
* **四张加成表**（照抄参考实现 `getGroupBonus`，档位 ≥70·≥60·≥50·≥40·≥30·≥20·≥10·其余）：
  * 宠物 `[7,8,9,41]`：`[2,4,6,8,10,89..96,232]` 各 +100/80/60/50/40/30/20/10；
  * 坐骑 `11`：`57`（致命点）/`173`（无视伤害减免）= 700…50，`130`（攻击次数）= 7…1；
  * 特殊 `[19,24,34,37,39]`：`171`/`169` = 1000…50，`56` = 500…20；
  * 其余（普通武器防具）：`58`/`59`/`60` = 500…50，`141`（全武器伤害、耐久%）= 20…1。
* 导出 `handbookView` / `unlockHandbookPage` / `unlockOwnedItems` / `refreshHandbook` /
  `lightAllHandbook` / `handbookBonus` / `handbookLevel`。

### 2. 存档字段与「谁是唯一真源」

```
p.handbook = {
  unlocked: {"1:13": [条目编号…]},   // 玩家点亮过什么（唯一真源）
  lit: false,                        // 用过「点亮所有图鉴」
  powers: {"58": 9500, …}            // 派生缓存：加成合计
}
```

`powers` 是算出来的，每次状态变化 + 每次进世界都 `refreshHandbook()` 重算 ——
好处是换一张加成表，老存档下次登录就能生效；同时 `native-character-stats.mjs`
读它时**不需要 import handbook**（`native-character-stats ↔ restoration` 已经是循环，
再挂一手容易出意外）。

### 3. 协议接线（`lib/official-service.mjs`）

* `32101` → `32102`：带角色时给真实 `unlock / level / rate / canUnlock`，`power=1`
  （客户端 `updatePage` 用 `info.power>0` 判断「暂未开放」，power=0 就整页灰掉）。
  不带角色时保持「全未点亮 / canUnlock=false」的纯目录视图（既有契约）。
* `32103` → `32104`（整页条目编号 + 新 level/rate）+ `32109`（新加成）+ `store.save()`。
* `handbookPage(1,13,role)` 会自动点亮？**不会** —— 32101 是查询，一行都不写角色（见下面教训）。

### 4. 加成落地（`lib/native-character-stats.mjs`）

原版 `Model.getSkillPowerValue(type,key)` 的第一段就是 `this.getPower(key)`，而
`getPower` 里写着 `t += RoleGodData.getPower(...)` 与 `t += BookGroupModel.getBookGroupPower(...)`。
服务端对应的桩是：

```js
getSkillPowerValue:(type,key)=>key>0?((type===1?(powers.get(key)||0):0)+(featurePowers.get(key)||0)+(bookPowers.get(key)||0)):0
```

即图鉴加成与特征加成（`featurePowers`）同一层、同样不按技能类型过滤 —— 这是
「面板显示」与「服务端战斗」用同一个数的地方，对不上的话就是「面板写 +500、实际加 50」。

### 5. 「点亮所有图鉴」道具

* 定义在 `lib/handbook-item.mjs`（单独一个模块，避免 `official-data → handbook` 互相 import）：
  `id=800110`、`type=28`、无 power、`stackNum=99`。
  注册点在 `lib/official-data.mjs` 的 `ensure()` 里（和 `localEnchantments` 同一处，
  必须**在索引 Map 建立之前**）；编号常量在 `lib/local-items.mjs`，
  并进 `PINNED_SUPPLY_ITEM_IDS`（补给商人 · 消耗品分类最前面，免费领）。
* 为什么等待类型是 `BAG_NO_WAIT(0)`：客户端 `createPlayerBagMessage` 上游那段
  `b=BAG_NO_WAIT` 的分支 —— 无 power 的 type 28 道具既不是药、也不是孵化/宝箱/绑定，
  于是 `b` 保持初值 0。客户端对 `BAG_NO_WAIT` 就是 `sendProto` + 本地自己扣一件、**不等回包**。
* 服务端在 `lib/restoration-service.mjs` 的 `12001/action3` 里按 `itemId` 提前认领
  （在 `jobBooks` / 药水兜底之前）：校验 `waitType===0`、`quantity>0` → `consumeItem` →
  `lightAllHandbook`（`lit=true`）→ `store.save()` → 推 `32109` + 公告 `10509`；
  失败时按既有写法把角色还原（`Object.assign(p,before)`）。

### 6. 客户端文案（`web/offline.js`）

原版 `getGroupTypeDes(group,type,level)` 靠 `getPowerDesc(info.power, info.powerValue + info.addValue*档位)`
—— 一次只描述得出来**一条**属性，而图鉴每一档都是好几条一起加（宠物全属性 + 宠物伤害、
坐骑致命点 + 无视伤害减免 + 攻击次数…）。所以整段覆盖成参考实现那张字符串表，
档位阈值与加成表一一对应；`level<=0` 仍返回「无」（照原版）。

> `web/*.js` 是静态资源：电脑版直接加载 `web/offline.js`，APK 由
> `安卓打包/standalone/build.mjs` 把 `web/` 平铺到站点根 —— 所以**不用**两边挂补丁，
> 也不进 `client-patch-chain`（那条链只用于主包 `fff570bb….js` 的字符串补丁）。

## 五、教训（这一版真正踩到的）

1. **32109 只许发一组合计值**。第一版我按 `handbookGroups().infos`（4 组）各发了一份同样的
   加成表，想着「组是给客户端看的」。实际上 `onHandBookPowerInfo` 会把**所有** info 的
   `powerValue` 累加进同一个静态 map（`group` 那一位它根本不读）→ 客户端把加成乘了 4 倍。
   测试里当场抓到（`38000 !== 9500`）。改成单组（`group=0`）后两边一致。
2. **道具定义字节的尾巴是条件写的**。原版 `Item.fromBytesAtts2` 的 type 28 分支：
   `power1/powerValue1/power2/powerValue2/vipLevelReq` 之后，**只有 `power1===181`（附魔卡）
   才继续读 `power3/powerValue3`**，然后才是 `needShowRate`。我照 `enchantment-data.mjs`
   的 Writer 链写全了三对 power，于是解码器多出 4 个字节读不掉
   （`Reader.finish()` 报 `Unconsumed bytes 4 at 113`）。无 power 的道具必须少写那两项。
3. **查询类接口不许改角色**。第一版 `handbookState(p)` 是「取（必要时创建）」，
   32101 只是查询却把 `p.handbook={unlocked:{},lit:false}` 挂到了角色上 —— 测试的
   `assert.deepEqual(p,before)` 立刻红。现在拆成两只手：
   * `handbookState(p)`：**只读**，老存档 / 没打开过图鉴的角色拿到一个不进存档的空壳；
   * `ensureHandbookState(p)`：写路径（点亮 / 道具 / 进世界重算）才用。
   （AGENTS「查询类接口不许改角色」这条又一次救了场。）
4. **`protobufSchemas` 只认 `switch` 形态的生成代码**。单条件（`t>>>3==1 ? …: skip`）解不出来，
   得在 `tools/capture-decoders.mjs` 里手写 schema —— 已有 `s2c_HandBookGroupList` 的先例。
5. 加成确实很大（全亮后普通页 19 页 × `58:500` 起，`ATK_STR_NEARBY` 能到五位数）。
   这是参考实现的原样数值，本版**不改**；要调就地改 `BONUS_TABLES`（客户端文案表要同步，
   测试会逐档对数字）。
