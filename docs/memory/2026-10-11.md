### 架构事实（以后别重新推导）
- **没有 git**。整个工程不在版本控制下。
- **补丁链写了两份**：`server.mjs:89-90` 与 `安卓打包/standalone/build.mjs:85-104`，
  注释明写"顺序必须一致"，**没有测试守着**。
- **构建期打一遍补丁、运行期又打一遍**：`build.mjs` 的 VFS 清单里
  `client/<MAIN_PATH>` 指向 `/<MAIN_PATH>.orig`（未打补丁），注释说"server.mjs 还要自己打一遍补丁"；
  也就是每次启动都要重读 4.9 MB 重打全链。约束只写在注释里。
- **改客户端有两个入口且边界不清**：`lib/client-*-patch.mjs`（字符串注入主包）与
  `web/*.js`（额外脚本，index.html 里 23 个 script 隐式排序）。
- `server.mjs` 268 行里：70+ import、20 个内联 `type===` 分支、23 项 HTTP 路由表；
  分派是 20 层 `if(handleX(...))return;` 顺序敏感链（handleGame 必须最后）。
- 协议号裸数字；`analysis/modules/0019.js` 有完整枚举表，但只用来取 4 个常量。
- `data/` 三套"技能/道具目录"并存（official-data / recorded-content / career-skills），
  无血缘文档说明谁覆盖谁。
- 测试：65 文件 / 370 用例，`known-failures.json` 忽略 **47 条**长期失败（"新增失败=0"判定）。

## 第 35 版 · 运行期跳过重复打链（评审第 6 项的前半）

**问题**：standalone 里主包构建期已打过补丁，但 `build.mjs` 又把 VFS 清单里的主包
指向另一份未打补丁的 `.orig`，于是每次启动重读 4.5MB、重跑全链 —— 实测 **834ms**。

**改法**：`lib/client-patch-chain.mjs` 加 `WORLD_REQUEST_MARKER` + `isClientMainPatched()`，
`patchClientMain()` 开头做幂等判断（源里已有标记就直接返回）；`build.mjs` 不再产出
`.orig`，VFS 直接指向打过补丁的成品。

**实测**：对站点主包调 `patchClientMain` = **0ms**（原版 = 834ms）；站点主包 sha256
逐字节不变；站点里已无 `.orig`。守卫用例 +2 条，共 10 条全绿。
全量 **396 用例全过**。

**注意**：这是**打包运行时**的收益 —— Node 开发路径读的是 `client/` 里的原版，仍会正常打链
（启动仍是 ~1.8s / RSS 566MB）。

**patchCombatLimits 局部化没做**：它用 acorn 全量 parse 后按 AST 精确定位第 56 号模块的
`get`/`addValue`，并校验「2 函数 × 每函数 7 个 case」。退回纯文本会丢掉这层校验、
有误改别处的风险；省下的 700ms 只在开发路径上。要动就应**缩小 parse 范围**
（先轻量扫描定位模块数组切片）而不是纯文本匹配。

## 第 9 条（静态检查）调研 — 只调研未实施

用户问「评审第九条做完有什么好处」。实测数据（以后要开 prettier/eslint 不用重测）：

- **`node --check` 串行跑 270 个文件 = 64.6 秒**（每文件一个 node 进程，全是启动开销）。
  换 **acorn 进程内 parse = 441 ms**（快 146 倍），而 acorn 本来就是 dependencies
  （构建期锁 module 56 用的）。所以语法基线要用 acorn，不要用 `node --check`。
- **prettier 3.9.8 已装（在 dependencies 里）但没有配置也没有 script**。
  `lib/*.mjs` + `server.mjs` 共 **120 个文件，tabWidth=1 与 tabWidth=2 都判 120 个不合格**
  —— 原因不是缩进，是项目刻意的紧凑写法（`if(a)return b;` 一行连写）。
