# 2026-10-20 · 第 85 版：免费装备合成新增「自选鉴定属性」

> 前一天的日志见 `2026-10-19.md`（第 77—84 版）。这一版是用户新提的一条需求：
> 在单机菜单的「免费装备合成」里加一个「自选鉴定属性」的功能，每个鉴定格一个选项框，
> 把合成效果与属性数值都显示出来，**每个装备的鉴定都可以在这里自己挑**，不参考其他版本。

## 一、动机

「免费装备合成」原本只做两件事：改 **合成属性**（p3 合成格，`template[field]===131`）和
**合成技能**（`combinedSkill`）。鉴定（`template[field]===121` 的普通鉴定格、`power4—7` 的
进阶鉴定格）只能在**装备工坊**里做，而且是花卷轴、按已录范围**随机**取一条（本工程取该条的
最高数值）。

用户要的是：在做「免费合成」的地方，也能**自己指定每个鉴定格是什么词条、数值多少**，
并且一眼看到效果。这属于单机便利功能（不消耗材料），和「免费合成属性」同一个性质。

## 二、做法

### 服务端（`lib/`）

- `lib/item-affixes.mjs` 新增两个「只读范围」导出（和普通/进阶鉴定同一套数据源）：
  - `identifyRanges(template)`：普通鉴定格（`identifySlots`，121）逐格给出**可用**属性项；
  - `upgradeIdentifyRanges(template)`：进阶鉴定格（`power4—7`）同上。
  - 两者共用 `usableOptions` 过滤掉写不进 `short` 的项；**进阶那组只要有一格没有可用范围
    就整组返回空** —— 因为 `applyUpgradeFields` 按 `upgradeIdentifySlots` 的数量校验整组，
    给不全就会抛错，界面与校验必须同源。
- `lib/equipment-composition.mjs`：
  - `workshopState()` 每件装备多带 `identify` / `upgradeIdentify` / `upgradeAffixes`
    （界面据此渲染每格的选项框与当前值）；
  - `planComposition()` 新增 `mode:'identify'`：`picks` 覆盖**全部**普通鉴定格（数量必须相等），
    可选 `upgradePicks` 覆盖**全部**进阶鉴定格；逐格按 field 找到选项、校验 power 与数值范围，
    再写进 `target.affixes` / `target.upgradeAffixes`。
  - ⚠ 没有普通鉴定格的装备要传 `picks:[]` 且**不写 `affixes`**：写成空对象 `{}` 是 truthy，
    会让 `itemWithAffixes` 走进「字节补丁」分支（需要 layout + SHA 校验），对没有 layout 的
    装备直接抛「此物品尚未核验独立鉴定属性。」。

### 客户端（`web/`）

- `web/index.html`：操作下拉加 `<option value="identify">自选鉴定属性</option>`；
  把原来的「合成效果 / 属性数值」两行包进 `#composition-choice-fields`，另加
  `#composition-identify-fields`（内含 `#composition-identify-slots`）。
- `web/equipment-composition.js`：新增 `renderIdentify()` —— 按普通 / 进阶两组，
  每个鉴定格渲染一个 `.identify-slot`（下拉 + 数值框 + 「可选范围」+ 实时「合成效果」），
  默认选中当前词条、数值默认该属性上限；`collectIdentify()` 在提交时按行收集。
  切换装备 / 模式都会重渲染；只有普通格的装备不提交 `upgradePicks`。
- `web/offline.css`：`.identify-group` / `.identify-slot` / `.identify-range` / `.identify-effect`
  几条样式。`web/*` 是静态资源（电脑版直接加载、APK 由 `standalone/build.mjs` 平铺 `web/`），
  **不进 `client-patch-chain`**，也不用两边挂补丁。

## 三、坑

1. **`planComposition` 返回的是「存档实例」，不是合并后的定义**：`item.isUpgradeItem` 这种派生
   字段只在定义里有 —— 单测要验进阶写入，得用 `itemPacket(...)` + 客户端解析器 `readItem()`
   读回来（并且要拿**带 `upgradeAffixes` 的实例**去打包，只传 `{itemId,slot,quantity}` 打出来的是
   原始模板，`isUpgradeItem` 自然是 false）。
2. **进阶必须整组**：`applyUpgradeFields` 用 `Object.keys(affixes).length!==slots.length` 校验，
   少一格就抛「无效进阶鉴定属性。」；所以界面里进阶那栏要么全给要么不给。

## 四、验证

- `tests/equipment-composition.test.mjs` 新增 3 个用例：
  1. 4 格普通自选（写入每个格、合成格 power3 不受影响、合成技能保留、缺项 / 超范围 / 非整数拒绝、
     `workshopState` 带出 4 格范围）；
  2. 4 格进阶自选（`upgradeAffixes` 写入、走真实客户端道具解析器读回 `isUpgradeItem=true` 与
     power4/powerValue4、只给普通格时不带进阶、进阶组不齐报错、没有进阶格的装备带进阶组报错）；
  3. 协议往返（`COMPOSITION_APPLY` 回包状态 0 + 新状态 + 道具包，铜币与背包不花）。
- `npm test` **93 文件 / 683 用例全过、新增失败 0**；`npm run check` 0 错。
- 上机复验由用户做。

## 五、下一步

- 无。用户已确认「全部版本移植工作已完成，后续不再有新版本」；本条是新的单机便利功能需求。

# 2026-10-20 · 第 86 版：装备编辑器（本地装备属性覆盖层）

> 用户需求：「帮我做一个 html 的装备编辑器，需求是我可以自己修改装备的各项属性，
> 放在 `世界online_原版单机` 目录下」。做法对齐已有的 `技能编辑器.html`：单文件 HTML
> 双击即用、产出覆盖文件、服务端启动时套用。

## 一、先查证「改属性到底要改什么」（这一步决定了整个设计）

1. **装备定义从哪来**：`data/official-v305.json` 的 `items`（2505 条，其中 2134 条是装备 /
   武器，带 `definitionBase64`）。这是抓包产物，一字节不改。
2. **客户端看到的是什么**：`lib/restoration-packets.mjs` 的 `itemDefinition()` 对原生道具
   直接 `w.raw(definitionBase64)` —— 面板、图鉴、商店、奖励格发的都是**这段字节**。
3. **服务端算属性用的是什么**：`lib/native-character-stats.mjs` 先把 `itemPacket()` 的输出喂给
   主包模块 0032 的 `Item.fromBytesAtts2` 解出来再算。
   → **结论：只改 JSON 字段不改字节，游戏里一分属性都不会变。** 覆盖层必须重写 `definitionBase64`。
4. **能不能安全重写字节**：`lib/character-import-codec.mjs` 的 `equipmentBytes()` 是唯一的
   装备定义编码器（`character-import-codec.mjs` 的 `writeEquipment`，字段顺序 + 偏移标记）。
   实测：**2134 件官方装备逐字节重编码全部一致（0 条不符）**。这条是整件事的前提，
   现在固化在 `tests/item-overrides.test.mjs` 第一个用例里。

## 二、做法

### 服务端

- **`lib/item-overrides.mjs`（新）**
  - `ITEM_FIELDS` + `ITEM_FIELD_GROUPS`：全部可覆盖字段（名称 / 图标 / 品级 / 需求 / 三防 /
    power1—3、鉴定槽 bindPower1—2 / 武器 atkType、atk_time、atkMin、atkMax、hitrate /
    耐久、价格、孔数、套装 / 飞升·强化星、进阶鉴定 power4—7、附魔槽、说明文字…），
    每项带 `kind`（string / int / short / byte / bool / power / atkType）与范围。
  - `compileItemOverrides()`：逐条校验并归一；未知字段、越界、改 `id` / `type` / `handBookItem`
    一律**点名抛错**（覆盖文件写错必须立刻看得见，静默失效 = 「改了没反应」）。
  - `applyOverrideToItem()`：合并字段 → 重算派生字段（`powers` / `level` / `requirements` /
    `durability` / `localPrice` / `localIcon` / `attackTimes` / `hit`）→ `equipmentBytes` 重写
    `definitionBase64`。
  - `applyItemOverrides(items)`：原地替换命中条目，返回实际套用的 id 列表。
- **`data/local-item-overrides.json`（新）**：`{_readme, revision, items:{道具id:{字段:值}}}`，
  初始为空。读法与 `local-skill-overrides.mjs` 一致：**不用 `fs.existsSync` 门控**
  （APK 里 VFS 的 existsSync 对 `data/**` 恒 false），直接 readFileSync、ENOENT 当「没有覆盖」。
- **`lib/official-data.mjs`**：在 `ensure()` 的**最后一步、建 `{official, officialItems, …}`
  之前**调用 `applyItemOverrides(official.items)`。顺序是硬要求：
  - 前面的补丁可能会补道具（覆盖表要能改到它们）；
  - `applyCustomAdventures` 重建 1002/1011/1022/1032 的定义字节时会**逐字节比对原定义**，
    覆盖排在它前面会让它当场抛错；
  - 覆盖是原地替换数组元素，`officialItems` 索引随后才建，`restoration.mjs` 再 spread 出运行时
    `equipment` 表 —— 一处生效，面板 / 商店 / 战斗 / 任务奖励全跟着变。

### 编辑器

- **`装备编辑器.html`（新，578 KB）**：单文件、双击即用，风格与 `技能编辑器.html` 一致。
  - 左：搜索 + 部位/品级筛选 + 「只看已改」；右：按分组渲染的表单（字段、范围、原值提示都来自
    服务端那份 `ITEM_FIELDS`）。
  - 武器类才显示武器数据组；属性下拉直接从 `game-labels` 的 172 个中文属性名里选
    （121/131/181 这类**占位标记**标 `※`，不是真属性）。
  - 顶部实时摘要（攻击范围/攻击次数/三防/附加属性…）；底部可展开覆盖文件预览。
  - 保存：优先 `showDirectoryPicker` 直接写进 `data/`（写完提示重启服务端），
    不支持的浏览器退化成下载文件；另有「载入覆盖文件…」接着改上次的覆盖。
- **`tools/build-item-editor-data.mjs`（新）**：把 `ITEM_FIELDS` + 装备目录 + 属性名表
  以**列式数组**内嵌进 HTML 的 `<script id="item-editor-data">`（2134 件 / 493 KB），
  `--check` 比对不写文件（测试就是调它）。
  - 属性名表从 `技能编辑器.html` 的 `game-labels` 里取（**不依赖 `client/` 与 `analysis/`**，
    否则测试在没入库的机器上跑不了）；部位名用客户端 `typeBS` 那一排（头/衣/裤/肩…单手剑/双手剑…扇子）。

## 三、坑

1. **道具的 `byte` 字段在 wire 上是「有符号字节」**：`Writer.byte` 写 `n & 255`、
   `Reader.byte` 读 `int8`。官方数据里 `itemSet` 有 -43、`hitrate` 有 -1、`ascensionStar` 到 50。
   校验范围一开始按 0..255 写，结果「把每件装备的现有值原样填一遍」这条守卫立刻炸 ——
   现在 byte 放 -128..255，并把这条守卫留在测试里（第 5 个用例）。
2. **解码 `definitionBase64` 要自己补一段实例尾巴**：`fromBytesAtts1` 读的是 `itemPacket` 写在
   定义**前面**的尾巴（quantity / 耐久 / 宝石 / 槽位 / 标记位），单喂定义会 `Truncated`。
   测试里的 `decodeDefinition()` 补空尾巴再喂主包 0032 的 `fromBytesAtts2`，并断言
   「一个字节不多不少」——覆盖后定义写歪一点这里就会红。
3. **字段表只能有一份**：编辑器表单与服务端校验共用 `lib/item-overrides.mjs` 的 `ITEM_FIELDS`
   （由工具内嵌进 HTML），测试断言两边一致 —— 否则会出现「编辑器能改、服务端拒绝」或反过来。
4. **不要给覆盖层加 `x||0` 式默认值兜底**：`power1:0` 是「清掉这条附加属性」，被 `||` 吃掉就永远
   清不掉。
5. **（顺手修掉的老 bug）技能覆盖与 `applyCaptured81` 的顺序**：技能覆盖循环原来挂在 ensure()
   的前半段（`applyCaptured81` 之前），而后者会拿抓包字节与已有记录**逐字节比对**、不一致就抛
   `Conflicting captured81 skill <id>:<level>`。于是「在技能编辑器里改一个被抓包收录过的技能等级」
   = 服务端直接起不来、整片测试红。这一版收尾时正好撞上（你在技能编辑器里存了
   **548「解除魔法」22 级**的覆盖，`npm test` 立刻倒了一片）。改法：把覆盖循环挪到 ensure() 的
   最后一环（`applyCaptured81` / 问剑 / 守卫挑战等全部之后、建索引与 `applyItemOverrides` 之前）
   —— 覆盖是用户意图，本来就该最后说了算，顺带让 `applyCaptured81` 新灌进来的技能也吃到覆盖。
   `tests/captured81-maya.test.mjs` 里加了源码顺序守卫 + 「未覆盖的抓包技能字节不许变」的行为断言；
   同文件那条「注入是幂等的」也改成先把已注入的技能挪走再灌（否则覆盖过的字节必然对不上）。

## 四、验证

- `tests/item-overrides.test.mjs`（新，7 个用例）：逐字节重编码；覆盖只改点名字段且客户端解码
  结果正确、其余字段不变；非法字段/越界/改 id·type/空条目/未知 id 点名抛错；空覆盖不动任何条目、
  命中条目原地替换而其余对象引用不变；**把每件装备现有值原样覆盖一遍字节必须不变**；
  覆盖文件结构合法且每条能命中官方目录；编辑器内嵌目录与当前 `data/` 一致。
- 端到端（临时写一条覆盖起真实 ensure()）：`officialItems.atkMax` / `restoration.equipment.atkMax`
  / `itemPacket` 出去再由主包解码器读回 —— **三处都是新值**；未知 id 的报错文案也验过；
  验完把覆盖文件还原成空。
- `npm test` **94 文件 / 691 用例全过、新增失败 0**；`npm run check` 0 错。
- 浏览器冒烟（headless）：页面无报错、600 条列表、切装备渲染 52 个字段、改数值/下拉后
  预览 JSON 与「已改」角标实时更新、武器类多出武器数据组、还原按钮生效。
- 上机复验由用户做（改一件装备 → 保存到 `data/` → 重启 `启动单机.cmd`）。

# 2026-10-20 · 第 87 版：技能编辑器加类型/职业筛选，效果名全部中文化

> 用户需求：「技能编辑器优化一下：加一个筛选框，能选定自动、被动、主动的技能，也能按职业筛选；
> 技能效果槽里的英文部分翻译成游戏里显示的中文，方便我选取效果。」

## 一、英文名的根因（不是「客户端没文案」）

`tools/build-skill-editor-data.mjs` 生成标签表时，会执行主包里 `Tool.getPowerDesc()` 的
`case e.POWER_X: return …` 分支来拿官方文案。原来的正则写的是：

```js
/case e\.(POWER_[A-Z_0-9]+):\s*return ([^;]{1,500}?);/g
```

`return` 后面**写死了一个空格**。而压缩产线包里两种写法都有：

- `case e.POWER_STR:return p>=0?"力量+"+c:…;`（三元，`return ` 带空格）→ 能匹配；
- `case e.POWER_REMOVE_STATUS:return"清除目标"+…;`（直接返回字符串，`return"` 无空格）→ **漏掉**。

漏掉的编号 `rawText` 里没有，最后兜底成 `POWER_XXX` 去掉前缀的英文常量。逐个数过：221 个效果
编号里有 **53 个**是这样退回英文的（79 清除状态、82 技能命中、97 复活回血、157—166 护主承伤、
176—186 各类内部标记…），不是客户端缺文案。

## 二、做法

### 生成器（`tools/build-skill-editor-data.mjs`）

1. 正则改成 `return\s*`，并且表达式在 `;` **或** `}` 处收尾（压缩包常把最后一个 case 的
   `return …}` 之间的分号省掉）：
   `/case e\.(POWER_[A-Z_0-9]+):\s*return\s*([^;{}]{1,500}?)\s*[;}]/g`。
2. `MANUAL_FIX` 扩充到 40 多条，只覆盖两类：
   - 分支依赖运行时对象 / 状态编号，执行不出完整句子：79/88（`e.getBufferString(p)` 的 `p`
     是**状态编号**，不能把某个具体状态写进名字）、80/82/97/98/99、113—117、120/167；
   - 游戏里本来就不显示文字的「内部标记」：103/105/106/108/109/110/111/131/176/177/179—
     182/185/186/304，以及原版完全没用的 36/66/196。
3. 新增可选字段 `note`（随标签表一起内嵌），解释特殊数值：79/88「数值填状态编号」、
   120/167「数值÷10 才是倍率」。编辑器选中该效果时显示在数值框下方。
4. 统计里的 `missing` 改成「名字仍等于英文常量」的条数（原来 `!x.n` 恒为 0，等于没在数）。
   现在生成结果是 **221 条 / 无文案 0 条**。

### 技能编辑器（`技能编辑器.html`）

- 左栏新增两个下拉（与来源、搜索、「只看已改」串联）：
  - **类型**：全部 / 被动 / 自动 / 主动（值 1/2/3，文案取自标签表 `skillTypes`；
    第 4 项「阵型」不是技能类型，不放进筛选）；
  - **职业**：全部 / 各职业（带条数）/「未标职业（装备/怪物）」；职业表按**实际载入的数据**
    现算，不写死；排序按条数降序。
  - 类型判定用 `skillTypeIds(rec)` 取**逐级** `type` 的并集 —— 同一个技能不同等级可以改类型，
    只要有一级是主动就能被「主动」筛出来。
  - 列表计数会带上当前筛选（如「共 23 个技能（被动 · 侠客）」）。
- 效果下拉不再出现英文：全部 221 条都是中文；带 `note` 的效果在槽下方显示 `ⓘ` 提示，
  下拉/数值框的 `title` 里保留 `POWER_XXX` 与写入值，排查时仍能看到编号。

### 装备编辑器（连带重跑）

`tools/build-item-editor-data.mjs` 的 172 个属性名是从**技能编辑器**的 `game-labels` 里取的
（这样子目录缺 `client/`、`analysis/` 时测试也能跑）。标签表一变，`tests/item-overrides.test.mjs`
的「内嵌目录与当前 data 一致」就会红 → 必须重跑：

```bash
node tools/build-item-editor-data.mjs
```

# 2026-10-20 · 第 88 版：装备编辑器排版修复（长下拉不再压到标签）

> 用户截图反馈：「附加属性、强化与进阶鉴定这些标签跟输入框都重叠了，放多一行，不要挤在一起。」

## 一、根因

`.field` 原本是**单行 flex**：标签固定 148px + 右侧 `.ctl`（下拉/输入框 + 灰色说明）。
而属性下拉的选项文字很长（`121 · 鉴定格（随机词条）`），`<select>` 的固有宽度被最长选项
撑到 200px 以上；`.hint` 又是 `white-space:nowrap`。外层 `.grid` 的列宽只有
`minmax(300px,1fr)` → 下拉 + 说明一起溢出格子，压到右边（或下一列）的标签/输入框上。
窗口越宽列越多、每列越窄，重叠越明显。

## 二、做法（只动 CSS + `fieldInput()`，数据块没碰）

1. 新增 `.field.stack`：**标签一行 / 控件一行 / 说明一行**。只有三类字段用它：
   `kind==='power'`（附加属性、鉴定槽、进阶鉴定、附魔）、`kind==='atkType'`（攻击类型）、
   以及带 `hint` 的字段（鉴定格的内部标记数值）。
2. 控件行 `flex-wrap:wrap`，下拉 `flex:1 1 100%`、说明 `flex:1 1 100%` → 无论列多窄都不会
   再和下拉抢同一行；说明改成正常换行，不再截断。
3. 单行字段也补了保险：`.field .ctl select{max-width:100%;min-width:0}`、
   `.field .hint{min-width:0;overflow:hidden;text-overflow:ellipsis}`、`label` 加 `min-width:0`。
4. 鉴定格/合成格那个「数值」输入框是只读的内部标记，原来会和上一格重复显示同一句说明 →
   现在只保留 `title` 悬浮提示，字段回到单行，表单不再被同一句话拉长三遍。

## 三、验证

- 浏览器（真 `data/`，747 圣诞衣服，52 个字段）：逐字段比较 label / ctl 的
  `getBoundingClientRect()` —— 单行字段 `label.right <= ctl.left`、堆叠字段
  `label.bottom <= ctl.top`，**0 处重叠**；11 个字段走堆叠布局。
- `tests/item-overrides.test.mjs` 14 用例全过；`node tools/build-item-editor-data.mjs --check`
  一致（只改了 CSS 与渲染函数，内嵌数据没变）。
- 上机看效果由用户做（双击 `装备编辑器.html` 即可，不需要重启服务端）。

# 2026-10-20 · 第 90 版：伤害计算器（导入存档 / 木桩）

> 用户需求：「这个战报还是不要了，帮我去掉吧，“查看”里面的信息已经够我判断了。
> 你帮我写一个 HTML 版本的伤害计算器，就是我可以导入角色存档，然后选择相应的角色，
> 配置自动技能和主动技能，打木桩测试伤害。」

## 一、为什么改成网页 + 本机 API

原版战斗在客户端本地算伤害，服务端只拿得到 12502 的胜负。想离线看「这个技能打多少」，
最稳的做法不是再挂一层战斗日志，而是**直接复用服务端已有的真实属性/技能定义**，
在网页里按客户端公式跑木桩：

- 面板：`nativeCharacterBattleStats()`（第 90 版新增，和 `nativeCharacterStats()` 共用
  `nativePlayer`，经客户端 `ModelConst.get()` 读装备/附魔/宝石/套装/被动/称号/城市特征/
  本地装备覆盖）。
- 技能：`activeSkills()`（与服务端战斗包同一份定义，含技能编辑器覆盖）。
- 公式：照抄主包模块 0251 的 `calcDirectDamage` / `calc` / `calTouchDmg`，
  默认 `isPreviewBeta=true`。
- 左右手：照第 76 版客户端补丁 `buildAttackPlan()`；总攻次仍是
  `ATK_TIME+skill.atk_time`（夹 1..99），变的是逐手武伤/武器类型分配。

这样网页只负责「配置 + 展示」，不用在浏览器里重写一套属性系统。

## 三、公式与踩坑

- **顺序**：0251 先掷命中、再算伤害（未命中也会消耗武器随机数），然后才是暴击、格挡、
  强韧、护盾；照抄这个顺序，同 seed 才能复现。
- **致命率分母是目标等级**（`15*critical/level`，没有 +12）；**格挡率分母是攻击者等级**
  （`7*(block-ignore)/level`），实际判定再夹 70。
- **`isPreviewBeta=true`**：物理攻击点数用 `ATK_STR_NEARBY/RANGE`、`ATK_AGI_NEARBY/RANGE`，
  不再叠加 `ATK_STR/ATK_AGI`；物理减免只看 `DEF_STR_NEARBY/RANGE` / `DEF_AGI_NEARBY/RANGE`。
- **强韧是千分比**：`calTouchDmg` 里 `TOUGH` 上限 700（70%），不是百分比点数；
  流血/衰弱会先把目标 TOUGH 减半。
- **法系武伤只对武器类型 19/34/37/38/39 生效**；诅咒/祝福在 `calcWithType(BATTLE_DAMAGE)`
  里返回 0，不要给它们补「最低 1 点」。
- **自动技能只自动折算「能确定是自身攻击增益」的正向 power**：技能 powers 没有目标标记，
  无法可靠区分自身 buff 与目标 debuff。`collectAutoBuffs()` 只映射攻击 28/29/30、攻击点
  58/59/60、攻次 130、命中 54/56、致命 57、破甲 69、法穿 75；其它项列进「未自动计入」，
  目标减益/回复/护盾仍由「临时修正」手动填。勾选框默认开，避免用户选了「魔化武器」却看到
  伤害没变化。⚠ 持续时间/冷却没有建模，整段模拟按增益常驻处理。
- **技能标签生成器**必须容忍压缩包的 `return"…"`（无空格），否则会静默退回英文常量；
  这是第 87 版踩过的坑，这里用同一个 `技能编辑器.html` 的 labels。
- **计算器静态页也是 `web/` 白名单**：电脑版漏了 404、APK 由 `build.mjs` 平铺；
  `tests/damage-calculator.test.mjs` 守住 `WEB_PATHS`、构建指纹和「页面不许内联脚本」三处。
- **CSP 是这次最隐蔽的坑**：页面是 `script-src 'self' 'unsafe-eval'`，内联 `<script>` 直接被拦，
  但 HTML/CSS 仍正常渲染，所以肉眼看不出错。以后写 `web/` 页面一律把 JS 放外部文件。

# 2026-10-20 · 第 91 版：装备覆盖后仍能鉴定/强化/附魔/赋灵

## 一、症状

用户用装备编辑器改了「圣诞衣服」747，进游戏后点鉴定/强化/附魔，提示
「物品定义已变化，请重新核验鉴定字段。衣服(进阶)」；赋灵不确定。

## 二、根因

- `lib/item-overrides.mjs` 会把覆盖后的定义用 `equipmentBytes` **重写
  `definitionBase64`**，这是第 86 版刻意做的（客户端收到的就是这段字节）。
- `lib/item-affixes.mjs` 的 `itemWithAffixes()` 仍按抓包时的
  `data/item-affix-layouts.json` 校验 `definitionSHA256`（第 135 行）：
  `bytes` 是覆盖后的字节，哈希当然对不上 → 所有需要改实例的工坊操作（鉴定、
  强化、附魔、赋灵、合成技能、进阶）一起失败。
- 不能只把哈希改成覆盖后的值：覆盖允许改名称/说明等变长字段，一旦长度变化，
  layout 里的**偏移**也会整体移动，按偏移写字节会写坏定义。

## 三、做法

- `lib/item-overrides.mjs`：`hasItemOverride()` 改为缓存一份 id 集合，避免每次
  itemPacket 都重新编译覆盖表。
- `lib/item-affixes.mjs`：新增 `overriddenItemWithAffixes(template, instance, layout)`：
  - 仅对 `hasItemOverride(template.id)` 的装备生效；
  - 仍在字段层面按原 layout 校验「这个槽位是否存在 / 附魔字段是否存在 / 星级字段是否存在」，
    避免覆盖装备变成可以随便写不存在字段；
  - 依次合并 socketCapacity / enchantment / affixes / star / combinedSkill /
    upgradeAffixes / spiritSeals；
  - 最后用 `finishEquipment(result)` **整份重编码** `definitionBase64`，覆盖字段与本次操作
    一起保留；非覆盖装备继续走原 SHA-256 + 偏移补丁路径，字节保持抓包原样。
- 覆盖装备的普通鉴定仍要求 `identify` 段里有对应范围（747 目前只有
  power1/power2/bindPower1/bindPower2；要进阶鉴定需在编辑器里补 power4—7 范围）。

- `npm run check`：353 文件 0 错。
