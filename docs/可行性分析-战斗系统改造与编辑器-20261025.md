## 一、自动技能加触发概率（**2026-10-25 修订：单技能语义**）

> 需求澄清：不是「多个自动技能之间按概率抽一个」，而是**给某个自动技能本身加一个触发概率**
> ——例：角色只勾了「魔化武器」，配置 30%，则每回合轮到它时 30% 施放、70% **完全不施放**
> （不显示、无任何加成）。

### 现状（代码依据）

```js
// analysis/modules/0251.js:603  doAutoSkill(e) —— 单个单位在「自动阶段」的处理
if (e instanceof _["default"]) { ...怪物走 AI... }
var o = this.getAutoSkillIDByRound(e);      // 玩家/宠物：取本回合该放哪个技能
this.doUseSkillById(e, o, n);               // ← 真正施放

// analysis/modules/0251.js:621  getAutoSkillIDByRound()
var i = e.getAutoSkillCount();              // 勾选的自动技能数量
var o = this.round % i;                     // ← 严格按回合轮转
return e.autoSkillID[o];

// analysis/modules/0251.js:340 回合流程：先自动阶段，再手动指令阶段
for (...) this.doAutoSkill(i);              // 自动阶段（342）
e = this.sortModelListBySpeed();
for (...) { var o = this.getPlanData(i.position), n=!1; if(o) n=this.doPlayerPlan(i,o); }  // 344-350
```

**语义确认（正好符合需求）**：只勾 1 个自动技能时 `count=1`，则**每回合都会轮到它**；
只要在该分支里「掷骰不中 ⇒ 直接 return（不调 doUseSkillById）」，这个单位本回合就没有任何动作
——自动阶段跳过、手动指令阶段也没有它的指令（`getPlanData` 返回空）⇒ **空过回合，不显示、无加成**。

### 关键约束：概率**不能**写进技能数据

- 技能字节是定长结构（`lib/character-import-codec.mjs` 的 `skillBytes`：id/level/name/type/…/anime1-3/position/statusBit1-3），**没有概率字段**，硬塞会破坏客户端解析。
- 覆盖层有字段白名单（`lib/local-skill-overrides.mjs` 的 `OVERRIDABLE_FIELDS`，注释明确「= skillBytes 能写进 wire 的字段，越界的键会被拒绝」）⇒ `autoChance` 写进 `set`/`perLevel` 会被挡。
- 结论：**概率是「本地玩法配置」，与技能字节无关**，单独存、单独下发。

### 改造方案（4 处，全部改动都很小）

1. **配置**：新增 `data/local-auto-skill-chance.json`
   ```json
   { "_readme": ["自动技能触发概率（%）。只影响客户端是否施放，不改技能数值。"],
     "chance": { "108": 30, "205": 100 } }
   ```
   （也可以放在技能覆盖层的**同级独立段**里：`{skills:{…}, autoChance:{…}}` —— `loadData` 只校验 `skills` 存在，多余键不报错。但独立文件更干净，推荐独立文件。）
2. **下发**：服务端加一条「动态全局变量」路由（项目已有 4 个同款先例）：
   ```js
   // lib/http-routes.mjs 照 /equipment-rules.js 的写法
   {kind:'path',path:'/skill-auto-chance.js',
    reply:({res})=>answer(res,200,mime['.js'],'window.worldolAutoSkillChance='+JSON.stringify(autoChanceGlobals())+';')}
   ```
   加进 `WEB_PATHS` 不需要（`kind:'path'` 路由是直接应答的）；`web/index.html` 里在 `offline.js` 之前引一行。
3. **APK 侧**：`安卓打包/standalone/globals.mjs` 导出 + `entry.mjs` 的 `installGeneratedGlobals` 铺到 `globalThis.worldolAutoSkillChance`（3 行，照 `equipmentRules` 的现成写法）。
4. **客户端补丁**：新模块 `lib/client-auto-skill-chance-patch.mjs`，包装 `Battle.prototype.doAutoSkill`：
   ```js
   const p = (globalThis.worldolAutoSkillChance||{})[skillId];
   if (p != null && Math.random()*100 >= p) return;   // ← 70% 分支：直接空过本回合
   原 doAutoSkill.apply(...)
   ```
   注意：要在「取到本回合技能 id」之后再判（即复刻 `getAutoSkillIDByRound` 的取值，或包装 `getAutoSkillIDByRound` 让它返回 -1 表示跳过 —— **包装 `getAutoSkillIDByRound` 更省事**：返回 -1 时原生 `doAutoSkill` 自己就会 `return`，不改动原逻辑）。

### 难点 / 风险

- **低**。推荐做法是包装 `getAutoSkillIDByRound`（比包装 `doAutoSkill` 更小侵入）：原来返回 `round % count` 对应的 id，改成「若该 id 配了概率且掷骰不中 ⇒ 返回 -1」，`doAutoSkill` 里 `0 > o` 的判断会自然 return，行为就是空过。
- 「不释放」时的表现：该单位本回合无动作（已由上文回合流程确认），符合「不显示、无加成」。
- 多个自动技能 + 概率同时启用时，掷骰不中会让**轮转顺序照样推进**（`round` 每回合 +1），即「这次轮到 B，B 没触发 ⇒ 空过」而不是「顺延到 A」—— 符合直觉；如果希望顺延，需要额外记录（建议先不做）。

### 技能编辑器需要同步改（回答「已有编辑器是不是也要改」）

**要改，但只加一栏，且写另一个文件。** 具体：

| 项 | 改什么 | 说明 |
|---|---|---|
| 技能详情面板 | 加一个「自动触发概率（%）」输入框，0—100，留空=100 | 只对 `type=2`（自动/回合技能）显示，被动/主动不显示 |
| 落盘 | 写 `data/local-auto-skill-chance.json`（不是 `local-skill-overrides.json`） | 覆盖层白名单会拒绝 `autoChance`，必须分文件 |
| 导出/导入 | 「下载覆盖文件」多导一个文件；导入时合并读两个文件 | 现有 `readJson("local-skill-overrides.json")` 旁边加一份 |
| 提示文案 | 在字段旁注明「此为本地玩法配置，不改变技能数值」 | 避免和「改效果」混淆 |
| 列表展示 | 技能列表行尾显示 `30%` 角标（有配置时） | 一眼看出哪些技能配了概率 |

改动量估计：**约 60—100 行**（一个输入框 + 一个读写字段 + 一处导出）。风险为零（不碰 wire 编码）。

> 顺带说明：这也是后续 B 层编辑器（自动技能概率 / 随机目标 / 阵位加成）的通用模式 ——
> **凡是「引擎字节里没有的玩法开关」，都走「独立配置文件 + 动态全局变量 + 客户端补丁」三件套**，
> 绝不往技能/装备字节里塞。

## 二、随机目标（敌方随机 N 人 / 我方随机 N 人）

### 现状（代码依据）

目标选择是**纯客户端函数**，服务端完全不参与（`lib/` 里没有任何 `getSelectArea`）：

```js
// analysis/modules/0251.js:2504  Battle.prototype.getSelectArea(e, t, i)
var o = getSearchTypeByArea(i);            // i = 技能 area 值
switch (o) { ALL / ENEMY / FRIEND / MY_SELF / MY_OWNER }
...
switch (i) {
  case SKILL_AREA_SINGLE:      a = getColumnTypeTarget(t, 1, false); break;
  case SKILL_AREA_UP_DOWN_FIVE:a = getColumnTypeTarget(t, 5, false); break;
  case SKILL_AREA_ENEMY_ALL:   ...  // 敌全体
}
```

**关键发现：原版已经支持「按条件选目标」**，area 表（`analysis/modules/0004.js`）末尾有：

```
SKILL_AREA_ENEMY_HP_LEAST = 31   敌方血量最少
SKILL_AREA_ENEMY_HP_MOST  = 32   敌方血量最多
SKILL_AREA_ME_HP_LEAST    = 33   我方血量最少
SKILL_AREA_ME_HP_MOST     = 34   我方血量最多
```

即 area 0—34 已用，**35 以后是空的**，而「随机选」和「按血量选」的实现形态完全一样（都是先筛出候选列表再挑）。

### 改造方案

1. 包装 `Battle.prototype.getSelectArea`：命中自定义 area 值时走随机逻辑。
   ```js
   新 area：35=敌随机2、36=敌随机3、37=敌随机5、38=我方随机2、39=我方随机3、40=我方随机4/full=我方随机全体
   候选 = getSelectArea(原 area 对应的「全体版本」) 过滤存活 → 洗牌取 N
   ```
2. 洗牌用现有 `d.Tool.rand`（0251.js 里 AI 已用过随机）。
3. 数据侧：技能条的 `area` 字段直接填新值 —— **技能编辑器改一个数字就生效**。

### 难点 / 风险

- **低-中**。真正的坑是 **AI/自动战斗的目标预选**：`searchAICursor`（0251.js）会预先算好目标位置给 `doUseSkill`，随机目标如果只在 `getSelectArea` 里随机，AI 侧的位置提示会对不上。做法：随机逻辑放在 `getSelectArea`（真实结算口径），并让 `searchAICursor` 对新 area 退化成「随便给一个存活目标」。
- 多目标技能（随机 5 人）要做「去重 + 存活过滤 + 数量不足时返回实际数量」，别返回 null（null 会让整个技能判定为无效）。

## 三、主动技能多段动画（打 A → 走回 → 打 B）

### 现状（代码依据）

技能演出是一条**子控制序列**，`Control.prototype.executeSkill`（`analysis/modules/0241.js`）里写得非常清楚：

```js
// SKILL_POS_FRONT 分支（近战冲锋型技能）
createBattlePlayerAnimation(ATTACK_START, ATTACK_MOVE)   // 起手 → 冲锋动画
createBattlePlayerMove(冲到目标身前)                      // 移动位移
createBattleDoAttack(目标列表 h)                          // 出手（这里产生伤害与特效）
createBattlePlayerAnimation(ATTACK_FALLBACK)             // 收招
createBattlePlayerMove(走回原站位)                        // 位移回来
createBattlePlayerAnimation(STAND)                       // 站定
```

**这套序列本身就是「冲过去→打→走回」**，第 3 项要的只是「把中间那段打两遍，第二次换个目标」。

而且**改目标的先例已经存在**：第 93 版前的社区版补丁里有 `centerFrontTarget`，做法是直接改 `aniControl.datas` 里的目标字节（`data.position=0; readByte(); ...; writeByte(新目标)`），并且真机验证过可行。

### 改造方案（建议分两步）

**第一步（简单版，先见效）**：不改序列，只把「出手目标」换成 N 个目标里随机挑的一个，**分多次战斗回合**完成多段（即：技能打一个目标，后续回合自动追击其余目标）。改动最小，无演出风险。

**第二步（真·多段）**：在 `executeSkill` 的 `setSubControlList(N)` 之前，把序列构造两遍：

```js
第一轮：目标 a1 → ATTACK_START/MOVE/DO_ATTACK/FALLBACK/MOVE(回位)
第二轮：目标 a2 → ATTACK_START/MOVE/DO_ATTACK/FALLBACK/MOVE(回位)
最后：STAND
```

每轮之间需要：**重置 `aniControl.datas` 的目标字节**（沿用 centerFrontTarget 的手法）、**重新取 `getSelectArea`**、**确保 `createBattleDoAttack` 两次调用不会互相清除 `effectControlList`**（代码里 `this.effectControlList = null` 只清一次，两轮要分两次构造）。

### 难点 / 风险（本报告唯一「高」）

1. **伤害结算时序**：`createBattleDoAttack` 内部既产生伤害也产生特效。两轮之间若结算包（战斗结果）已经发出去，第二段就会「有动画没伤害」。要确认战斗包的结算是在整条 control 序列结束后才发（需要验证 `isDone()` 与结算上报的关系）。
2. **攻击计划时间限制**：我们有 `client-attack-plan-patch`（MIN/MAX_HIT_TIME），多段会拉长单次施放时长，可能触发上限被截断。
3. **打断/取消**：战斗中途死亡、逃跑、战斗结束时，第二段可能残留控制对象（需要 `onRelease` 清理）。
4. **真机验证成本高**：每改一次要跑一场战斗看演出，无法靠单测覆盖（第 93 版技能特效的三轮热修就是教训）。

**建议**：先做「固定 2 段」并绑定到少数几个测试技能，跑通再放开配置。

## 四、阵法按位置差异化加成

### 现状（代码依据）

阵型数据（`lib/formation-data.mjs`）：

```js
{id:1, name:'天覆阵', teamcount:2, power1:28, value1:22, power2:29, value2:16, power3:27, value3:11}
```

- 有 `teamcount`（生效队伍数/人数阈值），但**只有 3 组统一的 power/value，没有「第 1 位/第 2 位」的字段**。
- 客户端叠加点（`analysis/modules/0056.js:2819`）：
  ```js
  null != this.formationSkill &&
    ((_ += this.formationSkill.getPowerValue(i)),   // 平加项
     (d += this.formationSkill.getPowerValue(o)));  // 百分比项
  ```
  `this` 是**单位自己的 PlayerVO**，读的是同一个 `formationSkill` 对象 ⇒ **同队所有人加成完全一样**。
- 服务端（`lib/restoration.mjs`）的 `powers(p,'equipment')` 也是统一合并，用于面板战力与校验。
- **额外发现**：`analysis/modules/0042.js`（宠物类）里没有 `formationSkill` ⇒ **宠物目前完全不吃阵法**。所以「宠物全体加减伤」不是改造，而是**新功能**（价值更高）。

### 改造方案

1. **数据层**：新增覆盖文件（不动 `formation-data.mjs` 的原版 16 阵），例如 `data/local-formation-slots.json`：
   ```json
   { "1": { "slots": [ {"powers":[[28,22]]}, {"powers":[[16,15]]}, {"powers":[[6,20]]} ],
            "pet": {"powers":[[16,10]]},
            "slotsMode": "byPosition" } }
   ```
2. **客户端**：包装 `PlayerVO.prototype.getPowerValue`（或 `getBaseValue`），从「当前单位的战场 `position`」映射到阵位序号（服务端下发或在战斗开始时按位置排序），再查上表。
   - 宠物：包装宠物类的同类方法，命中 `pet` 段。
3. **服务端**：`restoration.mjs` 的 `powers` 同步按阵位合并（单机场景下主要影响面板显示与战力估算，一致性要求可放宽）。

### 难点 / 风险

- **中**。三处都要改（客户端属性、客户端宠物、服务端合并），漏一处就出现「面板显示一个数、战斗里另一个数」。
- **阵位从哪来**：战场 `position`（0—9 站位）需要映射成「队伍内第几人」。建议：按 `position` 升序在己方存活单位里排名（第 1 个=一号位），逻辑简单且不依赖服务端。
- 属性键（power 值 2/3/7/8 等）已有映射函数 `clientFormationPower`，可直接复用。

## 五、怪物编队模拟器

`monsters` 就是 **10 个站位**的怪物 id（0=空位）。

**「自设编队 + 落地挑战」的完整模板已经在项目里跑着**：

- `lib/guard-challenges-data.mjs`：纯数据定义自定义编队（`groupId: 12100/12101/...` + monsters 数组），已上线并可用；
- `lib/climb-tower.mjs:197,223`、`lib/trial-challenge.mjs:152`：运行时注册
  ```js
  officialMonsters.set(id, copy);
  for(const group of official.groups) officialGroups.set(group.groupId, group);
  ```
- 落地入口：守卫挑战（NPC 菜单）/ 无限试炼 / 永泽塔 / boss 直达 —— 四种入口都有现成接线。

### 改造方案

1. 新增 `data/local-encounters.json`（玩家自设编队）+ `lib/local-encounters.mjs` 在 `official-data.ensure()` 之后注册怪物/编队（照 climb-tower 的写法）。

3. 编队字节：`wireBase64` 需要按 `monsters` 重编码 —— 服务端有现成的编码器（`lib/official-packets.mjs` / `codec.mjs`），照 `dungeon-repairs` 的做法生成。

### 难点 / 风险

- **低-中**。主要是「入口 + 注册时序」（必须注册在索引建立之前，AGENTS.md 已记这条）。
- ⚠ 落地挑战必须保证 `acceptBattleID` 指向真实编队，否则 `missionBlockers` 会以「战斗数据尚未采集」挡掉任务（第 93 版修的 9106 就是这个坑）。
- 自定义编队建议用高位号段（如 30000+），避免和原版/已注册编队撞号。

## 六、怪物编辑器

### 现状（代码依据）

怪物字段**异常完整**（实测 409 野狼，共 50 个字段）：

```
基础：id name icon1 level monstertype
血蓝速：hpMax mpMax speed
攻击：atkType atkMin atkMax atk_time
攻/防三系：atk_str/atk_agi/atk_magic 与 def_str/def_agi/def_magic
        （每系都有 _nearby/_range 变体）
命中暴击：hitrate hitMagic critical ignoreCritical criticalDmg
抗性：ignore_back ignore_magic_back ignore_block ignore_insight ignore_touch ignore_wil
       wil tough block brkArmor insight def_field back magic_back
特殊：life_absorption mana_absorption magic_penetration bornStatus newReflection
下发：wireBase64
```

- **`bornStatus`** = 天生状态（404 个怪全有，字符串位图）⇒ 你要的「天生状态」直接可编辑。
- **没有 `skills` 字段**：怪物技能不是挂在怪身上，而是走 **`monsterWireBase64` + `monsterAI`**：
  - `lib/official-data.mjs:155` 注释：「就在 official.skills 里（sources 带 monsterAI），战斗包发的是 monsterWireBase64||wireBase64」
  - `lib/local-skill-overrides.mjs:164` 已经处理了这条路径 ⇒ **改怪物技能数值，覆盖层已支持**。
  - 客户端怪物 AI：`getSkillByAI`（0251.js）→ `monsterAI.conType`（条件列表）→ `getConSkill`（条件对应技能）。

### 改造方案

1. **属性编辑**：`data/local-monster-overrides.json`（照 `local-item-overrides.json` 的模式：原值留底 + 字段覆盖 + `wireBase64` 重编码），在 `official-data.ensure()` 的精确时序套用（提前改会抛 `Conflicting captured81`，这是本项目踩过三次的坑）。
2. **天生状态**：`bornStatus` 字符串位，编辑器做成「勾选式状态位」即可。
3. **自带技能**：
   - 现已可行：改已有怪物技能的数值/等级（覆盖层）。
   - 需要逆向一轮：`monsterAI.conType` 的条件编码 + `msg` 文本 + 技能绑定关系 —— 弄清后就能「给任意怪加任意技能」，编辑器做成「条件→技能」的列表编辑器。

### 难点 / 风险

- **低-中**。属性编辑几乎没有风险（数据驱动 + 已有覆盖层模式）。
- **唯一不确定项**是 `monsterAI` 的条件编码（conType/msg/targetPos），需要在 `official.skills` 里找几条带 monsterAI 的样本逆向。**这是编辑器能否「加技能」的分水岭**，建议先花半天做这个逆向验证。
- 改了 `wireBase64` 必须重新编码（照 `skillBytes`/`skillBytesMonster` 的做法），否则客户端拿到的还是旧数据。

## 七、自制 HTML 编辑器的难度

### 先例（项目内已有三份）

| 编辑器 | 行数 | 落盘 | 生效方式 |
|---|---|---|---|
| `技能编辑器.html` | 1127 | `data/local-skill-overrides.json` | 服务端重启套用 + 客户端技能面板 |
| `装备编辑器.html` | 1015 | `data/local-item-overrides.json` | 同上 |
| `伤害计算.html` | 293 | 不落盘（只算） | 直接读服务端数据 |

**结论：一个「数据型编辑器」的量级 = 1000 行左右**，架构已验证（读原版数据 → 覆盖层 JSON → 服务端套用 → 客户端可见）。你可以完全照这三个的结构写。

### 但六项需求分三个层次，难度不一样

| 层次 | 内容 | 编辑器难度 | 原因 |
|---|---|---|---|
| **A 层·纯数据** | 怪物属性/天生状态、怪物编队设计 | ★☆☆☆☆ 容易 | 只是表单 + JSON，落盘后服务端一读就生效。**照抄装备编辑器即可** |
| **B 层·行为配置** | 自动技能概率、随机目标、阵位加成 | ★★★☆☆ 中 | 编辑器本身只是表单，难点在**运行时要读这些配置**：要新增 cfg 文件 + 服务端下发到客户端 + 2-3 个客户端补丁消费。每次加配置项 = 补丁里加一个读取分支 |
| **C 层·演出脚本** | 多段动画 | ★★★★☆ 难 | 不是「填数值」而是「编排序列」。要做到自由编辑，等于给客户端演出层写一个 DSL + 解释器。**建议先做固定模板选择（2 段/3 段、目标模式），不做自由脚本** |

### 建议的落地路线（按投入产出排序）

**第 1 步：怪物与编队管理器（A 层）** —— 一个 HTML 页面搞定第 5、6 项
- 怪物列表 + 50 字段表单（分组折叠：基础/攻防/抗性/特殊/天生状态）
- 编队可视化（10 格拖放，选怪入位）→ 生成 `local-encounters.json`
- 「一键试打」：写入后重启即生效，可在 boss 直达地图直接挑战
- 估算：约 1000-1400 行，与装备编辑器同量级。**投入产出比最高，建议先做**

**第 2 步：战斗行为配置面板（B 层）** —— 第 1、2、4 项的编辑器
- 自动技能：每技能一行「概率/权重/最多次数」
- 随机目标：技能 area 下拉改成「敌随机2/3/5、我随机2/3/4、全体随机」
- 阵法：16 阵 × 5 阵位 × 加成项的矩阵编辑（宠物单独一列）
- 估算：编辑器 600-800 行 + **4 个客户端补丁模块** + 配置文件 + 下发链路。工作量主要在补丁侧，不在 HTML

**第 3 步：多段动画模板（C 层简化版）** —— 第 3 项的编辑器
- 只提供「段数（2/3）+ 每段目标模式（当前目标/随机/血量最少）+ 每段动画组合（冲锋/原地/远程）」下拉
- 不做自由脚本编辑
- 估算：补丁 1 个（序列重排）+ 编辑器 300 行

### 现有三个编辑器各需要改什么（回答「已有编辑器要不要同步改」）

| 编辑器 | 自动技能概率 | 随机目标 | 多段动画 | 阵位加成 | 结论 |
|---|---|---|---|---|---|
| `技能编辑器.html`（1127 行） | **要改**：加「自动触发概率」一栏 + 另存 `local-auto-skill-chance.json`（约 60—100 行） | **要改**：技能详情里的 `area` 下拉补「敌随机2/3/5、我随机2/3/4」（约 30 行，纯选项扩充） | 可选：加「演出段数/目标模式」下拉（约 80 行） | 不用改（阵法不在这里） | 改动中等，风险低 |
| `装备编辑器.html`（1015 行） | 不用改 | 不用改 | 不用改 | 不用改（阵法是独立玩法） | **零改动** |
| `伤害计算.html`（293 行） | 可选：加「按概率折算期望 DPS」开关（约 60 行） | 可选：随机目标按期望值折算 | 不用改 | 要改：如果做了阵位加成，面板要能选「我在第几位」 | 建议等功能落地后再跟 |

**关键结论**：三个编辑器里只有**技能编辑器**必须同步改，而且改的是「加字段 + 写另一个文件」，
**不动它现有的 wire 字段逻辑**（所以不会引入新的编码风险）。装备编辑器和伤害计算器可以先不动。

### B 层玩法配置的通用三件套（后面所有「引擎里没有的开关」都照这个做）

1. **配置文件**：`data/local-*.json`（独立文件，不与抓包产物、不与 wire 覆盖层混放）；
2. **下发**：`lib/http-routes.mjs` 加一条 `kind:'path'` 动态路由生成 `window.worldolXxx`（照 `/equipment-rules.js`），
   同时 `安卓打包/standalone/globals.mjs` + `entry.mjs` 的 `installGeneratedGlobals` 各加 2—3 行；
3. **消费**：`lib/client-*.mjs` 补丁包装对应的客户端函数，配置缺失时**一律退化成原生行为**（不抛错、不阻断）。

这条三件套一旦跑通（第 1 项就是它的最小验证），后面的随机目标、阵位加成都只是「换一个配置项 + 换一个包装点」。

### 编辑器要避开的坑（都是本项目踩过的）

1. **写入时机**：覆盖层必须在 `official-data.ensure()` 的精确时序套用，提前写会抛 `Conflicting captured81`（`AGENTS.md` 有记）。
2. **`data/*.json` 抓包产物不许直接改**：编辑器一律写 `local-*-overrides.json`，原值留底（`original` 字段），否则重复打补丁会把上次的补丁值当原值。
3. **新 web 文件要进 `WEB_PATHS`**（电脑版白名单），新 `installXxx` 要带存在性保护。
4. **编辑器写完必须重编码 `wireBase64`**，否则客户端拿到的还是旧字节。

## 八、总体建议

1. **先做 A 层（怪物 + 编队）**：风险最低、当天可见效果，而且它同时解决「想自己改怪物」的痛点。
2. **再做第 1、2 项（自动技能概率、随机目标）**：这两个是「改一个入口就见效」的类型，可以和 B 层编辑器一起做，一个版本能覆盖三项需求。
3. **第 4 项（阵位加成）单独一个版本**：它要动客户端属性链 + 服务端合并，需要仔细核对「面板/战斗/战力」三处一致。
4. **第 3 项（多段动画）最后做，且先做固定 2 段**：它是唯一高风险的（演出时序 + 真机验证），建议先拿 1-2 个技能做试点，跑通再推广。
5. **编辑器不要一开始就追求「全部可编辑」**：分 A/B/C 三层推进，每层都能独立交付可用版本 —— 这样你不用等整体完成就能自己动手改。

**关于「不用每次问 AI」**：A 层完成后，改怪物属性/编队就完全自助了。B 层完成后，自动技能/随机目标/阵法也能自助。只有「多段动画」这类演出一旦要改新的组合方式，还是建议找 AI —— 因为它是代码级编排，不是数值配置。
